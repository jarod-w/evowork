# 本机会话复盘工具 · U1 评分材料 · 四处 agent 效果改进

2026-10-22，macOS arm64。真实 Electron + 发货内核（`build/kernel/mac-arm64`，d583e73c4d + P6/P7）；真实模型为用户提供的 `deepseek-flash`（`https://api.deepseek.com`）。本轮做的是同日评估列出的第 6 条（衡量）与第 2–5 条（使用效果）。

## 衡量（第 6 条）

- **`scripts/review-sessions.mjs`**：读本机内核会话记录，出一份复盘报告 —— 回合结局与错误码、请求次数与上下文峰值、策略拦截及理由、翻 App 安装包 / 内部状态、全盘搜索、中间文件落点、上下文构成、同一件事在多个会话里反复出现（按请求哈希与附件哈希，**默认不输出任何原文**）、记忆文件里的产品注入文本。单测 10 项。对本机 10 个真实会话（10-07 至 10-22）的基线：18 个回合（完成 16 · 中断 1 · 上下文溢出 1），210 次请求，输入 14.6M（缓存命中 98%），单次峰值 196K；策略拦截 12 次（全是「这是 EvoWork 自己的配置」）；翻 App 安装包 45 条命令；同一个附件在 3 个会话里反复出现；记忆文件里有 8 处产品注入文本。这些与当日手工复盘的结论一致。
- **真实模型预设补上 P0 另两家**：`kimi-k3`、`glm-5.3-flash`（能力位抄自 `known-models.ts` 的实测条目；**探测地址没有实测**，没有密钥）。
- **U1 评分材料**：`u1-artifacts.real.spec.mjs` 用固定种子输入跑 08 §5.4 的三个任务，产物收进 `test-results/u1-scoring/artifacts/`，读出机器能确定的事实，生成留给人填的评分表。**不替人打分。**
- `scripts/README.md` 写了「改完 agent 行为之后的固定复盘」三步。

## 使用效果（第 2–5 条）

| # | 改了什么 | 依据 |
| --- | --- | --- |
| 3 | Craft 指令与四个办公技能：中间文件（生成脚本、内容 JSON、只当配图的图、检查截图）放进本任务的临时目录（`mktemp -d "${TMPDIR:-/tmp}/evowork.XXXXXX"`，记下路径沿用），不进用户目录 | 内核的 `:workspace` 档默认可写 `$TMPDIR` 与 `/tmp`，不会因此弹审批 |
| 2 | 新增 `_shared/layout_check.py`：不渲染，用字体度量与字形表查文字溢出、缺字、越出页面、表格超出页面 / 版心、标题跳级；pptx / docx 渲染器出图后自动跑，结果随成功输出给模型（`layout_warnings` 要改，`layout_notes` 只是提示）。Hub 的 PPT 技能改为默认离线检查、在线图片校验须先在对话里征得同意（evowork-hub 仓库，**未发布**） | 本机版式预览要靠 LibreOffice，多数用户没有；10-12 那次 agent 手写渲染器查出的正是这几类 |
| 4 | 网关对 DeepSeek **只回传当前用户回合的思维链**（`DROPS_PRIOR_TURN_REASONING`）；复盘报告加了上下文构成 | 见下面的订正 |
| 5 | 会话原文目录单独成规则 `evowork-history`：范围不变、读写都拦，理由改成「这是对话记录，记忆按 MEMORY.md 与 rollout_summaries 作答」；审计页加了对应分类，并守住「每条硬拦截规则都有人话分类」 | 原先说「EvoWork 自己的配置」，会误导模型 |

**订正一个之前的判断**：评估里说「长任务上下文膨胀是因为截图一直留在上下文里」，**是错的**。10-12 那次 16 页 PPT 会话的实测：20 张图 5.6 MB 的 base64，每张只让请求多出 700–2000 token（DeepSeek 按图计固定预算）；上下文构成里思维链占 43%、模型写的脚本 18%、读文件输出 16%，图片约 0%。全部 10 个会话合计：思维链 30% 仍是最大头。

**思维链的实测**（直连 DeepSeek，几次小请求）：同一段两轮对话，第二轮保留第一轮的 `reasoning_content` 时输入 433 token，去掉 417 —— 差的正是那段思维链，且请求照常 200。同一回合内去掉这次也是 200，但网关**仍照旧回传当前回合的**（2026-09-08 曾因此回 400，厂商哪天收紧也不会坏）。Kimi / GLM 没有密钥，照原样回传。

内核记忆整理代理的另两类报错查过，都不归 EvoWork 改：`rm -f` 被拒是内核自己的危险命令规则（整理代理跑在「从不审批」档）；`update_plan` 不支持是内核给内部线程用的默认底稿提到了这个工具、却没给整理代理开（K1，不改内核）。

## 验收

- 原版 `pnpm run check` 退出 0，**3073 项通过、2 项既有跳过**；evowork-hub 的 `pnpm check` 21/21。
- 确定性真窗口回归（hook · 技能安装 · 视图 · 输入框）**15/15**。
- 真模型：身份与技能列表 **3/3**，附件 SKILL 安装指引 **1/1**，纪律 **2/2**（其中 C3 是两轮对话，走的正是「去掉上一回合思维链」的网关路径，没有 400）。
- U1 第一轮 **1/3**：两条失败都是新用例自己的问题 —— 用例级超时只有 5 分钟；被测 App 的 HOME 是临时目录，技能找不到办公扩展，模型满机器找 python（翻了安装包与仓库源码，还试着无界面启动用户机器上的 WPS），直到超时；审批卡在数到与点下之间收掉时会死等 30 秒。三处都修了（把 `EVOWORK_OFFICE_PYTHON` 交给 App · 用例超时 25 分钟 · 点不到就回到循环）。第二轮 **3/3（10.2 分钟）**。复盘那两次失败会话看得到第 3 条已被采纳：中间文件 12 次进了系统临时目录、0 次进工作区。
- U1 产物（deepseek-flash）：① 8 页 PPT，8 页都有文字，2 张表，字体 Microsoft YaHei；② Word 有目录、2 张表、A4，标题一级 7 个、二级 12 个；③ xlsx 汇总表 42 个 SUMIFS 公式、0 个写死的数、0 处断引用。版式检查对①②都是 0 条警告（只有「本机没装 Microsoft YaHei」的提示）。**评分表还没有人填。**
- 统计脚本跟着真实产物改了两处：随包技能把字体写在段落默认属性上、标题用「正文 + 大纲级别」表示，起初都被漏读。

密钥只经测试进程环境（会话暂存区 600 权限文件，跑完删除），仓库、`test-results/`、暂存区与全部测试临时 HOME 扫描 0 命中。

## 未验与边界

- 只跑了 deepseek-flash；Kimi / GLM 的预设探测地址、思维链行为都没有实测。U1 要评的正是 GLM。
- 新的 Craft 段落与技能说明只有上面这几轮样本，没有看比例。
- Hub 技能的改动在 evowork-hub 源码里，要走 Hub 的签名发布才到用户手上；它依赖的 `layout_check.py` 要新版 EvoWork 才有，旧版退回结构检查。
- 记忆更正笔记仍要等下一次记忆整理；之后跑 `review-sessions.mjs` 看「记忆里的产品注入文本」是否清零。
