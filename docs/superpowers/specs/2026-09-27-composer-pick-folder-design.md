## 0. 要解决什么

用户在 Composer 的「选择项目」菜单里直接选一个文件夹；后台把它建成项目（已经是项目就选中它），之后一切照旧。

项目仍然是一级概念。对 vibe coding 来说，一个仓库就是一个项目：侧栏按项目分组，项目说明（`AGENTS.md`）跟着项目走，任务归属按 cwd 落在哪个项目根下判定（projects spec D-P3）。本方案**不削弱**其中任何一条，只把「先去侧栏建项目、再回来选」这一步折进菜单里。

这个入口早就写进了 03 §4.5 的选项列表，只是一直没实现。
实现它会把几处现有缺口暴露得更频繁，所以本文把它们一并补上（§2 第 2–8 条）。

## 1. 已定的决策

| # | 决策 | 理由 |
|---|---|---|
| D-F1 | **项目保持一级概念**，不引入"不属于项目的工作目录" | vibe coding 以仓库为单位组织工作；侧栏分组、项目说明、项目页都以项目为中心 |
| D-F2 | 在菜单里选目录 = 建项目，或选中已有项目 | 用户只做一个动作；后台负责判断"这个目录是不是已经是项目" |
| D-F3 | **其它使用习惯不变**。确认过的例外只有两条：嵌套项目的任务归属（Q-F4）和侧栏项目排序（Q-F5） | 侧栏、项目页、引导、任务页的交互不动 |
| D-F4 | 所有建项目入口共用 `createProjectImpl`，去重与根目录规则加在**它里面** | 现有纪律（[renderer-bridge.ts:1179-1188](../../../apps/desktop/src/main/renderer-bridge.ts#L1179-L1188)）。加在那里，引导、项目页导入、新建对话框、Composer 四个入口一起受益，不会出现"只有一个入口过闸门"的情况 |

## 3. 设计

### 3.1 交互

```
[📁 选择项目 ▾]
┌─────────────────────────────────┐
│ ✓ evowork     ~/develop/evowork │
│   Q3 报告     ~/Desktop/Q3 报告  │
│ ─────────────────────────────── │
│ 📁 选择文件夹…                   │
└─────────────────────────────────┘
```

「选择文件夹…」固定在菜单底部，与项目列表之间有分割线（01 §5.19 的分组）。它是**动作**，不是可选中的值：Composer 的选中值永远不会变成它（01 §5.14 `actions` 变体，Q-F6）。

| 用户动作 | 结果 |
|---|---|
| 在系统对话框里取消 | 什么都不变，不提示 |
| 选的目录已经是某个项目（解析软链后是同一个目录） | 选中那个项目；Toast「这个文件夹已经是项目「X」」；**不新建** |
| 新目录，通过检查 | 建项目（命名见 §3.3）→ 选中它 → 侧栏、项目页、Composer 的项目快照一起刷新（02 §4.3 已有这条要求） |
| 被路径规则拒绝（§3.4 或现有硬拦截） | Toast 给出原因；选中值不变；项目表里没有新行 |
| 一个项目都没有 | 菜单里仍然有「选择文件夹…」，取代现在那句「还没有项目。任务会在默认目录里运行…」（这句话描述的正是第 4、6 条那个不该存在的默认目录） |

03 §4.5 里的「临时目录（不保存）」**取消**（Q-F3）。

**默认预选（Q-F3）：** 场景指定了项目就用场景的；否则预选**最近活动的项目**；一个项目都没有时不选。
「最近活动」的口径：该项目下（按 Q-F4 的最长匹配）最近一个任务的 `recency_at`；一个任务都没有时用项目的创建时间。
侧栏排序（Q-F5）用同一个函数，放在 `services/projects`。它与项目卡片的「最近活动」读同一个字段，区别只在没有任务时：卡片那里不显示这一段，这里退回创建时间。

**没选项目就发送（Q-F3）：** 不发送，展开「选择项目」菜单并提示「先选一个项目」，**保留输入**。选好之后**不自动发送**，用户再按一次。

### 3.2 后端

- **不新增 IPC 频道。** Composer 调已有的 `importProject`，在它的返回值 `ProjectMutationResult` 上加两个字段：`projectId`（新建或复用的那个项目）和 `reused`。项目页原来的调用方忽略这两个字段即可。不新增频道，也就不用改 `bootstrap` 的频道常量和 `electron-entry` 的端口（CLAUDE.md §9.1 说的那条接缝）。
- **`createProjectImpl` 内部的顺序：**
  ① 根目录规则（§3.4，新）→ ② 硬拦截（现有）→ ③ 去重（新）→ ④ 命名（新）→ ⑤ 落库（现有）→ ⑥ 镜像到内核（现有）。
  复用已有项目时跳过 ⑤⑥：不落库，不重复调 `project/create`。
- **去重的判定：** 对选中的目录做一次 realpath。已有项目的根逐个 realpath，失败时退回归一化后的字符串，然后逐个比较。项目很少，不需要加索引，也不用改表。
  系统对话框返回的是规范路径；大小写不敏感的卷上，用户手输大小写不同的路径会不会被当成两个目录，**没验过**，但所有入口都走对话框，不存在手输。
- **新建对话框**（用户自己填名字）撞上已有项目时，同样复用：对话框关闭，打开那个项目，给出同一句 Toast。

### 3.3 命名（Q-F1）

- 默认用目录名。代码仓库的目录名几乎总是仓库名。
- 和已有项目重名时，写成「目录名 · 上级目录名」，例如「src · evowork」；仍然重名，再追加「 (2)」「 (3)」。
- 只对**自动命名**生效。用户在新建对话框里自己填的名字不改。
- 外置卷的根，例如 `/Volumes/U盘`，命名为「U盘」。
- 建项目时**不往目录里写任何文件**。现状就是如此，保持不变。

### 3.4 根目录规则（Q-F2）

在 `services/policy/src/paths.ts` 里、`classifyPath` 旁边加一个判定：`workspaceRootRefusal(path, home)`，返回 `undefined` 或 `{ kind, reason }`。它回答的问题和 `classifyPath` 不同：`classifyPath` 判断**能不能碰某个路径**，这个判定回答**某个目录能不能当工作空间的根**。读 `~/foo` 本身无害，把 `~` 当根会让一切变成"工作空间内"。

| 拒绝作为项目根 | `kind` | 给用户的原因 |
|---|---|---|
| `/`，以及 Windows 的盘根（`C:/`） | `too-broad` | 这是整个磁盘，不能作为项目目录 |
| 主目录本身 | `too-broad` | 整个主目录作为项目的话，任务改动桌面、文稿里的文件时都不会再询问你。请选主目录下的某个文件夹 |
| 主目录的上级目录（如 `/Users`） | `too-broad` | 同上，范围更大 |
| `~/.evowork` 及其子目录 | `evowork-data` | 这是 EvoWork 自己的数据目录，任务记录和密钥库都在这里 |

**放行：** 外置卷的根（`/Volumes/<盘>`）；主目录下的任意子目录，包括 `~/Desktop` 本身。用户明确选了桌面，就是授权了桌面。

**同一个函数用在三处，不各写一份：**

1. `createProjectImpl`：两类都拒。覆盖全部建项目入口。
2. 所有用 `rootOf` 求 cwd 的地方（发送、选择附件、拖入附件）：两类都拒。旧数据里可能已经有这样的项目。遇到时拒绝并给出用户看得懂的原因，**不调 `thread/start`**。
3. 适配层：`thread/start` 与带 cwd 覆盖的 `turn/start`，cwd 命中 **`too-broad`** 就拒绝。这是唯一的咽喉：前两处负责给用户一个看得懂的原因，这一处负责"不管从哪条路来，这样的 cwd 都到不了内核"。
   `services/kernel-adapter` 因此新增对 `@evowork/policy` 的依赖，不成环：`policy` 只依赖 `logging`。

> **2026-10-01 定稿时订正：第 3 处原来放在 hook 上（`classifyPath` 遇到这类根时不当工作空间），现在改到适配层。**
> hook 只对 `hard-block` 动手（[handlers.ts:95-110](../../../services/policy/src/hooks/handlers.ts#L95-L110)），也问不了用户；写工作空间外要不要审批由内核沙箱决定，沙箱可写的根就是 cwd。
> 所以改 `classifyPath` 什么也守不住，配的测试也只是在断言一个没人读的判定结果（CLAUDE.md §9.1）。
> 代价是：用 CLI 等其他客户端建的、cwd 为 `~` 的任务，我们这边保护不了，原稿声称能保护是错的。
>
> **第 3 处只管 `too-broad`，是为了 Q20。** 助理的固定 cwd 是 `~/.evowork/assistant/`。它不是项目，不走建项目入口，但落在 `evowork-data` 的范围里；
> 适配层两类都拦的话，助理恢复上线时会建不出 thread。`evowork-data` 防的是"用户把 EvoWork 的数据目录选成项目"，这件事只会发生在第 1、2 处。
> `too-broad` 防的是"工作空间内"这个范围本身失去意义，不管 cwd 从哪来都成立。

**旧数据：** 不改表，不删项目。项目卡片沿用「路径已失效」那一档的警告样式，文案换成上表里的原因。

### 3.5 cwd 守卫

- **适配层：** `thread/start` 没有 cwd 就拒绝；cwd 命中 `too-broad` 也拒绝（§3.4 第 3 处）。[adapter.ts:982](../../../services/kernel-adapter/src/adapter.ts#L982) 是唯一的调用点，所以守在这里就守住了**全部**入口，包括发送和自动化。守的是"任何新任务都没有默认目录，也不会跑在整个磁盘或整个主目录里"这一类问题，而不是某一个入口。
- **桌面发送：** 没选项目时不调 `send`，行为见 §3.1。
- **自动化：** 见 Q-F8。
- **纵深：** 启动内核进程时显式指定 cwd 为一个专用的空目录。这样将来即使出现绕过适配层的新调用点，退回去的目录也不会是 `/`。要求：这个目录落在硬拦截范围内，出问题时表现为"拒绝"而不是"放行"。具体位置实现时再定。

### 3.6 附件（Q-F7）

首页没选项目时添加附件：不再调主进程然后报错，渲染层先判断，直接弹出 Toast「先选一个项目，附件会放进项目的 uploads 目录」，带「选择文件夹」动作（Toast 支持动作，见 01 §5.31）。选完**不**自动接着弹文件选择框。

### 3.7 不变的部分

项目页、引导第②步、任务页的交互都不变。侧栏只有两处变化：项目按最近活动排序（Q-F5），任务按最长匹配归属（Q-F4）。
引导第②步走的 `pickWorkspace` 自动获得去重和根目录规则：重走一遍引导不会再建出重复的项目。
任务进行到一半时切换项目，行为保持现状（Q-F9）。

## 5. 决策记录（2026-10-01 确认：全部采纳建议）

保留被否决的选项与理由，以后回看时知道为什么没这么做。

### Q-F1 · 自动命名规则 —— **定：A**

- **A（采纳）**：用目录名；重名时写成「目录名 · 上级目录名」；仍然重名，再追加「 (2)」。
- B：总是用目录名，允许重名。
- C：代码仓库读取 git remote 里的仓库名，其他目录用目录名。

重名的项目在菜单和侧栏里无法区分，而侧栏只有一行宽，放不下路径。C 要读 `.git/config`，收益很小：仓库目录名和仓库名几乎总是一样的。

### Q-F2 · 哪些目录不能作为项目根，旧数据怎么处理 —— **定：A**

- **A（采纳）**：§3.4 那张表（磁盘根、主目录本身、主目录的上级、`~/.evowork`）；放行外置卷的根。旧数据不改表，卡片标警告，发送时拒绝并给原因。
- B：在 A 的基础上，再拦 `~/Library` 这类"技术上可以、但普通人不会选"的目录。
- C：只拦 `/` 和主目录。

这四类目录都会让「工作空间内」的范围失去意义（§2 第 5 条）。`~/Library` 里需要保护的钥匙串、浏览器 profile 已经被硬拦截覆盖，再拦整个目录属于误伤。外置卷的根放行，是因为办公用户会把整个 U 盘当成一个项目。

### Q-F3 · 没选项目就发送；默认预选；临时目录的去留 —— **定：A**

**现状：** 有两个以上项目时，重启后首页默认什么都没选，发送后任务落在进程的当前目录（§2 第 6、7 条）。

- **A（采纳）**：
  ① 按 03 §4.5 已经写好的默认值，补上**预选最近活动的项目**（口径见 §3.1）。
  ② 仍然没选时按发送：不发送，展开「选择项目」菜单，提示「先选一个项目」，**保留输入**。选好之后**不自动发送**，用户再按一次。
  ③ 从 03 §4.5 删掉「临时目录（不保存）」。
- B：同 A，但选好之后自动接着发送。
- C：不预选，只做 ②。

① 是文档里本来就有的默认值，不算改变习惯，而且能让 ② 很少出现。② 不自动发送，是因为 cwd 决定了这个任务能不经询问改哪些文件，第一条消息发出前应该让用户看到选中的是哪个项目。③ 和 D-F1 一致：vibe coding 场景里临时目录不是需要的形态，而且原来写的"产物不会长期保留"和"产物就是交付物"相矛盾。

### Q-F4 · 嵌套项目的任务归属 —— **定：A**

**现状：** 侧栏按"完全相等"分组，卡片按"前缀"计数。在项目 `/repo` 下再把 `/repo/packages/a` 建成项目，一个 cwd 为 `/repo/packages/a` 的任务会同时算进两张卡片的数字。

- **A（采纳）**：两处统一成「匹配最长的项目根」，共用一个 `ownerProjectOf(cwd, projects)`，放在 `services/projects/src/membership.ts`。
- B：不改。

允许嵌套是对的（monorepo 里「整个仓库」和「某个子包」都是合理的项目），但同一个任务出现在两处，会让用户不再相信卡片上的数字（projects spec §2.1 写过这条）。**改变的习惯：** 用 CLI 等其他客户端、在项目子目录里建的任务，会从侧栏的「最近」移到对应项目下面。

### Q-F5 · 侧栏的项目排序 —— **定：A**

**现状：** 侧栏按创建时间倒序，只显示前 3 个。随手选的文件夹会把常用的老项目挤出侧栏。

- **A（采纳）**：改成按最近活动排序，口径与 Q-F3 ① 相同，两处共用一个函数。
- B：不改（严格遵守 D-F3）。

选文件夹变成一步操作以后，项目的数量会明显变多，按创建时间排序会让侧栏总是显示最新建的项目，而不是正在用的项目。**改变的习惯：** 侧栏项目的顺序。

### Q-F6 · 菜单里「动作项」的组件形态 —— **定：A**

- **A（采纳）**：给 `InlineSelect` 加一个 `actions` 属性，渲染在分割线下方；在 01 §5.14 登记为变体，与 `field` 变体写在同一处。
- B：在 `options` 里放一个特殊 id，在 `onChange` 里截住。

B 会让一个"动作"混进"值"的列表里：显示当前值、键盘导航、测试，每个读 `options` 的地方都得记得排除它。这正是 CLAUDE.md §9.1 说的"给守卫留的例外口子"。

### Q-F7 · 首页没选项目时添加附件 —— **定：A**

- **A（采纳）**：§3.6。Toast 带「选择文件夹」动作，选完不自动接着弹文件选择框。
- B：选完文件夹后自动接着弹文件选择框。

连着弹两个系统对话框，用户容易以为第一个选错了，又弹了一次。

### Q-F8 · 不选项目的自动化 —— **定：A（2026-10-01 订正了失败后的处理）**

**现状：** 自动化表单允许不选项目，调度时不带 cwd（§2 第 8 条）。加上 §3.5 的适配层守卫以后，这类自动化到点触发时会失败。

- **A（采纳）**：新建和编辑自动化时**必须选项目**。已经存在的、没有项目的自动化，到点触发时**立即暂停**，并通知「「X」已暂停：这个自动化没有指定项目。编辑它并选择项目后再恢复。」。本次运行记 `FAILED / ENVIRONMENT`，不起任务。
- B：守卫对自动化放行。

B 等于给守卫开了一个口子，而自动化是无人值守的，正是最不该落在 `/` 里跑的那一类任务。

> **订正：** 确认时的原文写的是"按 `ENVIRONMENT` 失败，然后走 Q8 的连续失败 3 次自动暂停"。这两句不能同时成立：
> `ENVIRONMENT` 类失败**不计入**连续失败（[failure.ts:18](../../../services/scheduler/src/failure.ts#L18)），按原文实现的话，这个自动化会每次到点都失败，而且永远不会暂停。
> 原意是"失败了要停下来，不要一直跑"。现在改为与「自动化还没有选择模型」完全相同的处理（[kernel-bridge.ts:111-122](../../../services/scheduler/src/kernel-bridge.ts#L111-L122)）：立即暂停、通知原因、记一次失败。
> 那条路径已经存在并经过测试，这里不发明新的处理方式。
>
> **附带发现（不在本方案范围）：** 07 §7 写「工作空间路径失效 → 自动置 PAUSED」，但代码里只记一次 `ENVIRONMENT` 失败，不暂停（[kernel-bridge.ts:125-136](../../../services/scheduler/src/kernel-bridge.ts#L125-L136)）。文档和代码不一致，另行处理。

### Q-F9 · 任务进行到一半时切换项目 —— **定：A**

**现状：** 在已有任务里切换项目，会改变这个任务的 cwd（§2 第 9 条）。「选择文件夹…」在任务页同样可用，所以也能在任务中途建一个新项目并切过去。

- **A（采纳）**：本方案不改变它，任务页的行为与切换已有项目保持一致。"任务开始后是否锁定目录"另立需求讨论。
- B：本方案顺带把任务页的项目选择器锁定（显示当前项目，不可更改，给出原因）。

锁不锁定目录是一个独立的产品问题（锁定会损失"在同一段对话里换一个仓库继续"的能力），不该搭本方案的便车。但要记录下来：中途换目录以后，前后两段的产物会分散在两个目录，任务在侧栏里的位置也会跟着变。
