## 0. 使用说明

### 0.1 优先级定义

| 级别 | 含义 | 判断标准 |
|---|---|---|
| **P0** | 首个版本必须有 | 客户安全 / IT 评审会直接问到,没有就过不了审批 |
| **P1** | 第二阶段 | 提升规模化和体验,首批客户反馈后再做 |
| **P2** | 后期 / 按需 | 差异化或锦上添花,需求不明确前不投入 |

### 0.2 编号规则

- `A*` = Agent 端(终端用户和 Agent 构建者使用的部分)
- `B*` = 管理端(管理员、安全、合规、运维使用的部分)
- `C*` = 跨领域非功能要求
- 编号格式:`模块.序号`,如 `B2.3`

### 0.3 前提假设(需要你核实或确认)

1. 首批客户为已经使用 AWS、可以接受"加密、不留存的跨区域模型调用"的企业。
2. 模型以 Claude(Bedrock)为合规主路径,其余模型通过 OpenAI 兼容适配器接入,不含中国开源模型。**v0.2 注:harness 本身只支持 Responses 协议,Claude 需经 B13.1 网关接入,见 0.E。** **v0.3 注:EvoWork 现有网关的内置厂商恰好是 DeepSeek、Kimi、GLM 三家国内模型(总纲 Q2 / Q16),外加一个通用 OpenAI 兼容通道;没有 Bedrock 或 Claude 适配。与本条假设冲突,见 0.G.3。**
3. 客户自己承担模型调用费用(走客户 AWS 账单),你只收取软件费用。
4. 以下涉及监管和云服务区域可用性的说明,截至 2026-10-31,变化很快,**上线前请以官方文档和当地律师意见为准**。

### 0.4 设计原则(贯穿所有功能)

1. **默认安全**:新建 Agent 默认没有任何工具、外发和长期记忆权限,需管理员明确授权。
2. **权限继承**:Agent 只能访问当前用户本来就有权访问的数据,不使用万能账号。
3. **可举证**:每个策略和每次关键操作都能生成给审计 / 安全团队的证据。
4. **模型可替换**:Agent 不绑定具体模型,通过别名和策略路由。
5. **轻量交付**:标准化容器 + 基础设施模板,尽量减少定制。
6. **失败时收紧,而不是放宽**:降级、异常、策略冲突时,选择更保守的路径。

## 0.B 关键结论

1. **harness 层覆盖了不少"运行时安全与治理"的需求**:沙箱、审批、执行策略、MCP、hooks、OTEL、托管配置(`requirements.toml` 与客户自托管 config server)。这些可以直接复用或作为接入点。
2. **企业能力基本都是缺口**:多用户 / RBAC / 租户、数据分级与 DLP、知识库、管理端、调度、部署模板。Codex 的定位是**单用户本地的编码 Agent**,这些不在它的范围内。
3. **模型层有一个关键冲突**:harness 的 provider 只支持 Responses API(`wire_api = "chat"` 已被移除)。它内置的 Bedrock provider 走 Bedrock Mantle 的 OpenAI 兼容端点(SigV4 认证,默认 us-east-1),模型 ID 是 **OpenAI GPT 系列**。我们之前定的"Claude 为合规主路径"**不能直接在 harness 里用**,需要网关或改造,见 0.E。
4. **Hooks 是接入 DLP / 审计 / 业务审批的最自然位置**,并且可由托管配置强制(`allow_managed_hooks_only`)。但"能否阻断、能否改写提示词和工具参数"需要逐项验证。
5. **默认带有对外联系的开关**(analytics、feedback、更新检查、Statsig 遥测、ChatGPT 登录等),私有部署必须逐项关闭并验证,见 0.D。
6. **内置记忆是面向编码的本地管线**,没有分级 / 权限 / TTL;建议接管而不是直接开启,见 A5、B4。

## 0.E 架构决策:模型层怎么接

| 方案 | 做法 | 优点 | 缺点 / 风险 |
|---|---|---|---|
| **A. Responses 兼容网关** | 自建(或复用现成项目改造)一个对 harness 暴露 `/v1/responses` 的网关,后端路由到 Bedrock Claude、Bedrock GPT、本地模型 | 保持 Claude 合规路径与 B2 的路由 / 分级 / 降级设计;网关本身就是 B2 的实现载体;不改 harness 核心 | 要做 Responses ↔ Claude 的协议转换(流式、工具调用、推理项、结构化输出);harness 的提示词和工具格式主要围绕 OpenAI 模型调优,**换成 Claude 的效果要评测** |
| **B. 以 Bedrock 上的 GPT 为合规主路径** | 直接用 harness 内置的 Bedrock provider(SigV4、Mantle) | 改动最小,今天就能跑 | 我之前**没有查到** GPT 在新加坡 / 日本 / 韩国的区域内或地理范围可用方式,需核实;与此前"首尔、新加坡区域内 Sonnet 5"的优势不一致 |
| **C. Fork harness 新增 Anthropic / Converse 协议** | 在 provider 层加新的 wire api | 少一跳网关 | 与上游合并成本高,早期不建议 |

**建议**:先做 **A 的 PoC**,同时核实 **B 的区域可用性**作为兜底;C 暂不考虑。两者都应放在阶段 0 里验证(B13.1)。这是基于源码阅读的工程判断,最终以实测为准。

**v0.3 现状**:EvoWork 已经走的是**方案 A**。`services/gateway` 对内核暴露 `/v1/responses`,内核 `base_url` 恒指向本机回环(总纲 D11),上游侧做 Responses ↔ Chat Completions 的全量翻译:流式事件重排、工具参数重组、reasoning 段不伪造、图片显式拒绝,并统一用量与 cache 口径。三家国内模型都对真实 endpoint 实测过。另有心跳与上游看门狗、上下文超长识别、截断和残缺工具参数不当作完成。缺的是**后端换成 Claude**:当前翻译层面向 Chat Completions 形状,接 Bedrock Claude(Converse / Anthropic Messages)需要新增一个 provider 适配;harness 的提示词换到 Claude 上的效果也没有评测过。方案 B(Bedrock GPT)和 C 都没有做过。

## 0.F 主要风险

1. **单用户本地 vs 多用户服务端**:每用户(或每会话)一个运行单元,资源成本和隔离方式要早定(B13.5)。
2. **上游迭代很快**(仓库当天仍有提交)。策略:不改核心,扩展走配置 / hooks / MCP / 网关 / 宿主层,必要补丁集中管理(B13.11)。
3. **部分协议是 experimental**(需声明 `experimentalApi`),升级可能破坏客户端;锁定版本并做契约测试(B13.13)。
4. **编码场景的默认假设**(shell、补丁、git)与办公 Agent 不同:要收窄工具面,避免办公用户获得 shell 能力(B13.7)。
5. **许可与品牌**:Apache-2.0 需保留 LICENSE / NOTICE;对外产品名称避免使用上游商标,请法务确认(B13.12)。

### 0.G.3 与本清单假设的冲突(需要产品决策)

1. **执行位置**:本清单(B13.5)假设 harness 在服务端以"每用户一个运行单元"运行;EvoWork 的执行面整体在员工电脑上,服务端不跑 Agent。选哪一条决定 B1、B3、B10、B11 的大部分工作量。18 篇给出的是"桌面执行 + 企业控制面"的折中。
2. **模型路线**:本清单以 Claude(Bedrock)为合规主路径、不含中国模型;EvoWork 已落地的是国内三家 + 通用兼容通道。网关框架可复用,Claude 需要新的 provider 适配和效果评测。
3. **默认值**:本清单要求新 Agent 默认零工具、长期记忆默认关闭(0.4 原则 1、B11.6);EvoWork 当前默认**开启**本机记忆的使用与生成,默认权限档可在工作区内读写和执行命令(需审批的动作仍弹审批)。
4. **国内办公生态与渠道**:EvoWork 的总纲 Q9 规定本期不做飞书 / 企微 / 钉钉;本清单 A1.11 把飞书、钉钉列为 P1。面向东南亚可以只做 Teams / Slack / LINE,但要显式取舍。
5. **界面语言**:EvoWork 界面只有简体中文(`lang="zh-CN"`,无多语言框架);本清单把英文列为 P0。

# 第七部分:待确认事项

1. **客户分层与目标行业**:首批行业和国家决定了场景模板(A6.5)和规则库(B3.3)的优先级。
2. **全球跨区域路由是否可接受**:这是东南亚客户能否使用云端模型的关键,建议在 PoC 前用访谈确认。
3. **Bedrock 各区域模型的最新可用性**:尤其是结构化输出、日本地理范围路由对新模型的覆盖,影响 A2.11 和 B2.4 的默认配置。
4. **GPT 在目标区域的可用方式**:未核实。
5. **日本 / 韩国的本地认证与采购要求**:影响 C1.4 的投入顺序。
6. **自研 vs. 复用开源网关**:模型网关(B2、B13.1)是否基于现成开源项目,需评估许可证、安全审计能力与企业支持;**harness 只认 Responses 协议,网关必须提供该接口**。
7. **首批连接器清单**:以客户实际使用的系统为准,避免一次做太多。
8. **团队人力评估**:如果第一阶段人力不足,可优先砍掉 P0 中偏体验的部分(如 A1.5 的非英 / 中语言、A1.7 的细节),保留所有与安全评审直接相关的条目。
9. **(v0.2)你的客户端目前实现到哪一步**:是直接对接 `app-server`,还是嵌入 CLI / TUI?已经实现了哪些 A1、A7、A9 的功能?这决定第〇部分表格里"需确认"项的真实状态。**v0.3 已回答**:EvoWork 是 Electron 桌面应用,经 `services/kernel-adapter` 对接 app-server JSON-RPC v2,不嵌入 CLI / TUI;逐条状态见 0.G 与各模块"EvoWork 现状"。
10. **(v0.2)模型路径**:Claude 经网关(方案 A)的工具调用稳定性;GPT 在新加坡 / 日本 / 韩国的区域内或地理范围可用性(方案 B)。
11. **(v0.2)hooks 的能力边界**:能否阻断、改写提示词与工具参数,钩子失败时的默认行为。
12. **(v0.2)容器内沙箱**:EKS / ECS 上 bwrap / landlock 的权限要求与替代隔离方案。
13. **(v0.2)外联与遥测**:无公网出口环境下的端到端验证结果(含模型目录、更新检查等默认行为)。
14. **(v0.2)多用户宿主层的成本模型**:每用户 / 每会话一个运行单元的资源占用,决定定价与容量规划。
15. **(v0.3)执行放在哪里**:继续 EvoWork 的"员工电脑执行 + 企业控制面"(18 篇),还是按本清单改为服务端多用户执行(B13.5)?这是本清单与现有实现之间最大的分歧,决定大部分 B 模块的工作量,应先于阶段 0 决定。
16. **(v0.3)模型路线是否并存**:面向东南亚 / 日韩时,是在现有网关上新增 Bedrock Claude provider,与国内三家并存;还是为这条产品线另起一套模型目录?涉及 EvoWork 总纲 Q2 / Q16 与本清单前提假设 2 的取舍。
17. **(v0.3)默认值是否改为"默认安全"**:本机记忆默认开启、随包工具默认可用,与本清单 0.4 原则 1 / B11.6 冲突。企业受管模式下是否由策略包改为默认关闭,个人模式是否保留现状。
