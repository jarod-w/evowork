# 21 · 项目记忆隔离与遗忘方案

2026-10-17。提案，未实施；不改变 [20](20-memory-import.md) 的当前能力承诺。

## 目标与当前缺口

项目 A 的任务不注入、检索或引用 B 的记忆；关闭读取与删除已存知识是不同操作。“忘记这个项目”必须阻止同步和后台提取把知识立即恢复，且不得损伤其他项目。来源副本删除不等于遗忘整理出的事实。任务历史、用户文件和源应用记忆是否删除必须分别告知。

当前发货 `d583e73c4d12` 的 V1 使用全局索引及正文库，scope 由整理/使用指令约束。本轮前的真实模型验证已证实其他项目能看见索引。公开协议只有整体 `memory/reset`，没有 memory scope、按来源遗忘、衍生关系删除或批次撤销。禁止在产品层通过读写内核 sqlite/记忆文件实现这些操作。

## 严格隔离候选

| 方案 | 优点 | 代价及限制 |
| --- | --- | --- |
| 上游增加记忆 scope，并在写入、整理、注入和检索前强制过滤 | 单个 app-server；可保留既有任务与项目体验 | 需要上游公开协议及完整持久模型支持；不能仅给摘要加项目标签 |
| 每个项目独立内核运行目录和进程，按项目路由官方 RPC | 不改内核，用现有独立本机存储构成上下文边界 | 多进程、任务路由、账号配置、插件、队列、审批、恢复、资源预算均需适配；现有任务迁移没有公开跨实例导入接口 |
| 摘要提示词或前端隐藏 | 成本小 | 不能阻止共享索引/正文被读取，不满足目标，排除 |

建议优先推动上游 scope 能力；在其不可获得且确有严格上下文隔离需求时，再开展独立实例验证。此时新增项目使用独立实例，旧全局记忆不自动拆分迁移；旧任务保留在旧实例并明确旧边界。暂不承诺把已经混合的知识可靠拆回各项目。

独立目录只隔离记忆注入和默认检索，不能阻止同一 OS 账号下拥有广泛文件权限的工具主动读取其他目录。若需求包括机密不可读，必须同时验证原生文件系统权限/沙箱覆盖记忆目录、符号链接、子代理和完全访问模式；做不到时不提供该保证。严格项目模式中不自动混入个人全局记忆。

## 按项目遗忘

推荐上游提供受支持的 scope 遗忘事务：停止该 scope 的同步/后台作业 → 使在途整理结果失效 → 删除来源副本与其衍生事实/向量/摘要 → 重建受影响索引 → 持久化遗忘屏障 → 返回可查询 operationId。任务历史默认保留，但遗忘前的相关历史不得再次自动成为记忆输入；重新学习需要用户显式授权。混合事实必须有来源依赖，不能只按路径删除文件。

若采用独立实例，项目整体 `memory/reset` 是可评估的基础，但仍要先停同步、停止并等待后台作业、禁用历史重新贡献，并验证 reset 与在途作业的竞态。现有 reset 本身不能保证全部步骤，所以目前不能把它包装成项目遗忘。清空后不得自动重新导入旧来源；来源应用原件与任务历史保留，界面说明其范围。

“撤销一次导入”单列后续：需要 importId → 来源版本 → 衍生知识的依赖关系。多批共享事实只能移除被撤销批次的贡献，不能抹掉其他有效来源。本方案不以全量清空冒充批次撤销。

## 分阶段交付与验收

1. 先做能力验证，不改当前生产路由。确认上游 scope 接口可用性；否则验证两个独立实例的完整任务生命周期及资源预算，登记架构变更后再实施。
2. 先覆盖新项目隔离，再评估旧共享记忆的用户可控重建。项目重命名、路径移动、多根目录、子代理、自动化、分叉与恢复必须跟随同一个稳定 scope 标识，不能只靠 cwd 字符串。
3. 最后实施遗忘事务与屏障。异常断电可查询恢复，不能丢失遗忘请求或把半完成显示为成功。

验收至少三个项目使用随机互斥标记：检查模型实际 developer 上下文、工具检索和回答；加入显式索取其他项目记忆的对抗请求。验证项目切换、子代理、恢复、模型切换、同步期间遗忘、整理期间遗忘、重启、历史再贡献及重新导入。对未授权项目，检查真实请求中零目标项目内容，而不只检查回答没有复述。遗忘后重复上述用例，其他项目标记仍可用；禁读和网络/文件权限分别验收。
