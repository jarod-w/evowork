## 1. 布局

默认是“侧栏 + 对话”两栏；结果工作区按内容与用户意图成为第三栏（01 §3.1）：

```
┌──────────┬────────────────────────────────┬──────────────────┐
│ 侧边栏    │ 对话区                          │ 结果区（可折叠）  │
│ 275      │ flex · 内容列 ≤768 居中          │ 42% · 420–720     │
│          │                                │                  │
│ 任务列表  │ ┌ 任务标题栏（标题栏带内）        │ 产物 / 文件 /     │
│ 在此高亮  │ ├ 消息流（19 类 Item）           │ 变更 / 浏览器     │
│          │ └ Composer（同 03 §4）           │                  │
└──────────┴────────────────────────────────┴──────────────────┘
```

- 有产物、文件或变更时，结果工作区**默认展开**（`⌘I` 切换）；没有可展示结果时不显示。用户手动收起后，同一任务的新内容不应抢开。
- 默认展示只适用于用户尚未表达开合偏好的任务；普通附件本身不算结果。
- 用户手动关闭后，本任务内禁止再次自动打开，直到用户主动打开；各任务记住最后选中的 Tab。
- 结果区展开后优先保证消息正文可读；窗口 <1100 时覆盖主区，不继续挤压对话。
- 侧边栏在任务页与首页完全一致（01 §3.3），只是当前任务项为选中态。

## 2. 任务状态：为什么必须自建投影表

### 2.1 内核给了什么

实测（2026-09-04 @ `728cb12fe5`，README F7/F8/F9）：

| 事实                                                                                                                                          | 出处                                            |
| --------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| `ThreadStatus` = `NotLoaded \| Idle \| SystemError \| Active { activeFlags }`；`ThreadActiveFlag` = `WaitingOnApproval \| WaitingOnUserInput` | `v2/thread.rs:1639-1656`                        |
| 未加载的 thread 状态恒为 `NotLoaded`，**不携带上次执行结果**                                                                                  | `v2/thread_data.rs:260`                         |
| `thread/list` **没有状态过滤，也没有日期区间过滤**                                                                                            | `v2/thread.rs:1368-1439`                        |
| `ThreadExtra` 是空结构体；`thread/metadata/update` 只能改 `projectId` / `gitInfo` —— **协议没有客户端自定义元数据槽**                         | `v2/thread_data.rs:167`、`v2/thread.rs:979-991` |
| 结果信息在 `turn/completed` 的 `TurnStatus`（`Completed \| Interrupted \| Failed \| InProgress`）                                             | `v2/turn.rs:32-37`、`:509-512`                  |

### 2.2 结论与派生规则

清单 §4.3 的六态**不能只由 `ThreadStatus` 得到**，清单 §4.2 的「按状态或日期筛选」**不能由 `thread/list` 得到**。因此服务层维护 `thread_projection` 表（09 §4.1），由事件流实时更新：

| 清单状态 | 派生规则                                                                               | 数据          |
| -------- | -------------------------------------------------------------------------------------- | ------------- |
| 进行中   | `ThreadStatus::Active` 且 `activeFlags` 为空                                           | 实时          |
| 待处理   | `ThreadStatus::Active` 且 `activeFlags` 含 `WaitingOnApproval` 或 `WaitingOnUserInput` | 实时          |
| 规划中   | 投影表 `mode = plan` 且存在 `plan` item 且用户尚未确认执行                             | 投影表        |
| 已完成   | 投影表 `last_turn_status = completed` 且当前非 Active                                  | 投影表        |
| 失败     | 投影表 `last_turn_status = failed`，或 `ThreadStatus::SystemError`                     | 投影表 + 实时 |
| 已中断   | 投影表 `last_turn_status = interrupted` —— **清单没有这一态，但用户会遇到**            | 投影表        |
| 已归档   | `thread/list?archived=true`                                                            | 内核          |

> **对总纲的修订**：§3.3 把「按状态/日期筛选」标为 [复用] 应改为 [自建]（README §6 M2）。另建议在清单 §4.3 补「已中断」——`TurnStatus::Interrupted` 是真实存在的终态，映射到"已完成"会误导用户，映射到"失败"会让用户以为出错了。UI 上按「已中断」独立呈现（`Badge neutral` + 「已中断，可继续」）。

### 2.3 状态机

```
                    turn/start
        ┌──────────────────────────────► 进行中 ◄──────────┐
        │                                  │              │
     (新建)                    ┌───────────┼──────────┐   │ turn/steer
        │                      ▼           ▼          ▼   │ 或 队列出队
   规划中 ──确认计划──► 进行中   待处理    已完成/失败/已中断─┘
        │                    (审批/追问)      │
        └────────────────────────────────────┴──► 已归档
```

- 「待处理」是**进行中的子态**（内核层面仍是 Active），但在任务列表里必须提到最前面 —— 它是唯一需要用户立刻行动的状态。
- 任何终态都可通过 `thread/resume` + `turn/start` 回到进行中（清单 §4.6）。

## 3. 任务列表（侧边栏）

### 3.1 分组结构

侧栏“项目”显示全部项目，点击项目行后展开该项目的最近 5 条任务；下方“展开显示”每次再显示最多 5 条，直到全部显示。“最近”汇总所有项目及无项目任务，与项目内列表均按最后活动时间降序，同一任务可在项目下和“最近”中同时出现：

```
项目
  📁 市场部
       季度汇报 PPT
       第 36 周周报
最近
  📌 查询当前黄金价格           1天前
```

- **置顶就是内置的 pinned 分区**，不额外做 `is_pinned` 字段（总纲 §6.1 已定）。用户自建 `ThreadSection` 可继续作为底层组织能力，在搜索/数据管理中使用，但不把多层分组常驻在主侧栏。
- 项目内任务和“最近”统一按最后活动时间降序；置顶标记保留，但不改变时间顺序，也不按 `ThreadSection` 再分组。
- “项目”和“最近”使用同一分组标题，点击独立折叠，默认展开、不显示数量；筛选时保留“最近”的命中 / 总数和重置入口。空列表保留标题，不添加常驻空态说明。
- 各项目任务默认收起，独立展开、收起和分页；不足 5 条显示实际数量，没有更多任务时隐藏“展开显示”。项目与最近的任务行统一按 28 行高 + 4 行距排列；项目任务标题缩进与项目名称对齐。
- 折叠后隐藏的任务不挂载、不上报 `onVisibleChange`，展开后恢复原有选中态与分页范围。项目和“最近”重复出现的任务 id 去重后上报。
- “最近”按每页 30 条增量挂载，滚动到底加载。**列表项渲染用虚拟滚动**（长期用户会有上千任务）。

### 3.2 任务行

`TaskListItem`（01 §5.5）。状态点颜色按 01 §6.1。子任务（`parentThreadId` 非空）**不出现在顶层列表**，只在父任务的对话流里以 `SubAgentActivity` item 呈现（§5.6）。

### 3.3 行操作（清单 §4.4）

悬停 ⋯ 或右键唤出 `Menu`：

| 操作             | 实现                                           | 备注                                                       |
| ---------------- | ---------------------------------------------- | ---------------------------------------------------------- |
| 置顶 / 取消置顶 | `thread/section/move` → pinned 分区    | 已接通时显示                                               |
| 重命名          | `thread/name/set`                      | **已接通**（2026-09-13）。标题是自动来的（§3.5），必须有人工纠正入口 |
| 移动到项目      | 更新任务的 `projectId`                | 已接通时显示                                               |
| 打开所在文件夹  | 本机 shell                             | 使用 `thread.cwd`                                         |
| 归档            | `thread/archive`                       | 归档后从列表消失，去“数据管理”                             |
| 删除            | `thread/delete`                        | 二次确认，且必须说明不会删除项目文件；若任务含电脑操控内容，必须同时清除 AX/截图所在 rollout、blob 与索引（CU-Q5=A） |

主路径只展示端到端接通的操作。分享、复制链接、分叉等动作在链路接通前隐藏，不得保留点击后只记录 `unimplemented` 的菜单项。

**电脑操控留存的删除语义**：归档只改变可见性，继续保留 AX 正文与截图。任务“删除”只有在底层历史、
图片/blob 和索引都被实际清除后才能报告成功；仅删除 EvoWork 投影表记录不满足 CU-Q5=A。实现必须用
临时测试内容做磁盘前后扫描，证明任务不可通过重启、恢复或搜索重新出现。

“保存到项目”通常不是一个动作——Q1=A 下任务天生在真实目录执行。若任务使用临时目录，该菜单项才出现，语义为“移动到正式项目”（移动目录 + 更新 `cwd` + 重建产物索引路径）。

### 3.4 搜索与筛选

全局“搜索”入口打开独立搜索状态；任务页侧栏不常驻复杂筛选图标：

搜索页数据源分两层：

- 标题匹配：`thread/list?searchTerm=`（内核支持，`v2/thread.rs:1428`）
- 内容匹配：`thread/search` (exp) + `thread/searchOccurrences` (exp)，结果分组显示为「对话内容命中」

高级筛选在搜索页的 `Popover` 中提供：

| 条件                                     | 实现                                                | 说明                     |
| ---------------------------------------- | --------------------------------------------------- | ------------------------ |
| 状态（多选，六态 + 已中断）              | **本机投影表查询**（内核不支持，§2.1）              | 这是投影表存在的主要理由 |
| 时间范围（今天 / 7 天 / 30 天 / 自定义） | 本机投影表 `updated_at`                             | 同上                     |
| 项目                                     | `thread/list?cwd=` 或 `?projectId=`(exp)            | 内核支持                 |
| 模型                                     | `thread/list?modelProviders=`                       | 内核支持                 |
| 是否有产物                               | 本机产物索引 join                                   | 自建                     |

> **当前实现边界（2026-09-13）**：独立搜索页已用 `thread/search` 同时呈现标题与
> 对话正文摘要，点击结果可直接打开旧任务；实验方法不可用时如实降级为本机标题搜索。
> `thread/searchOccurrences` 的单条消息定位与本节高级筛选仍未进入页面。
| 来源（手动 / 自动化 / CLI）              | `thread/list?sourceKinds=` + 投影表 `automation_id` | 混合                     |

筛选生效时 `SidebarSectionHeader` 变为「任务 (12 / 148) · 重置筛选」（清单 §4.2 要求的重置入口）。

**实现要点**：筛选走**本机投影表主导 + 内核校正**的顺序 —— 先在 sqlite 里按条件查出 thread_id 列表，再拉这批的权威元数据（避免投影表标题过期）。不要反过来（先全量拉再本地过滤），上千任务时会卡。

**第 ② 步怎么拉（2026-09-05 修订）**：本文原先写"用 `thread/list` 拉取这批的权威元数据"，
但 **`thread/list` 没有"按 id 过滤"的参数**（F8 的参数清单里没有），这一步照字面做不到。
实际可行的是两条并用：

| 路径 | 做什么 | 代价 |
|---|---|---|
| ① 可见页逐个 `thread/read` | 只对**当前可见页**（≤30 条）拉权威字段 | 有界；且只在筛选生效时发生 |
| ② 定期对账 | 启动时 + 每 10 分钟一次 `thread/list?useStateDbOnly` 刷新 title/cwd（09 §4.1） | 标题最多滞后 10 分钟 |

实现上两条都做：列表**先用投影表立刻渲染**（满足 §9 的"<300ms 出内容"），再对可见页做 ① 校正。
把 ① 限死在可见页是关键 —— 不限的话"筛选出 800 条"会变成 800 个 `thread/read`。

另外：投影表的排序除时间戳外还带 `thread_id` 作第二排序键。同一毫秒创建的任务
（批量导入、多个定时任务同时触发）只按时间排序时顺序不确定，UI 表现是**列表在两次渲染之间跳动**。

### 3.5 任务标题从哪来

内核**从不自动命名**：`Thread.name` 是 `Option<String>`，而 `thread/name/updated`
只在客户端显式调过 `thread/name/set` 之后才发（`app-server/src/request_processors/thread_processor.rs:638-658`）。
它把命名整个留给了 GUI。所以侧边栏里那些「未命名任务」不是"还没生成"，是**永远不会生成**。

标题由三个来源写入，**真源始终是内核**（09 §4.1），投影表的 `title_source` 只记"这个名字是谁给的"：

| 来源 | 什么时候 | 怎么来的 | 能盖谁 |
|---|---|---|---|
| `derived` | 任务创建时 | 第一条消息的第一个非空行 → 折叠空白 → **剥掉客套与句末标点** → 按码点截 24 字 | 只在没人写过时写 |
| `artifact` | 第一个产物落地时 | 技能上报的显示名（`mark_artifact --title`，08 §2.2 信号 ①） | 只盖 `derived` |
| `user` | 行操作「改名」（§3.3） | 用户自己输入 | 永远能写 |

#### 为什么不调模型起名

起名要花一次模型往返：钱、延迟、以及一条把用户正文发出去的理由。第一条需求本身
就是用户对这个任务最准确的描述，这与 `services/scheduler` 的自然语言触发解析
选择同一条路（不调模型），也与 K6 一致：**不为一个装饰性的字段新增出网动作**。

#### 产物命名为什么不算"调模型"

技能上报的显示名确实是模型写的 —— 但它是在用户**已经付过钱的那次生成**里顺手写的。
于是上面三条代价在这里全是零：没有新增调用、没有新增延迟、**没有新增出网路径**。
而它用的是"任务产出了什么"而不是"用户要什么"，后者才是标题真正要回答的问题。

四道闸门（实现见 `services/artifacts/src/task-title.ts`）：必须是技能上报（信号 ②③
只有文件名，`output.docx` 比用户原话差得多）· 必须是 `create` · 必须是第一版 ·
显示名不能就是文件名。**第一个产物赢** —— 一个任务产出三个文件时，标题在侧边栏里
跳三次比一个平庸的标题更糟，用户会以为出了错。

#### 为什么只剥客套、不剥动词

去掉「帮我」「请问能不能」「麻烦」这类框架词是纯词法的，安全。但**不砍内容动词** ——
分不清「生成一份季度汇报」的「生成」与「删除上季度的归档」的「删除」哪个可砍时，
一个都不砍：保留一个多余的动词只是标题长一点，砍错一个是把标题变成谎话。

## 4. 任务标题栏（在标题栏带内）

```
[← 折叠] │ 季度汇报 PPT    [Badge 进行中]          [打开结果] [⋯]
```

顶栏只保留任务上下文、高价值状态、结果入口和更多操作菜单；整条顶栏在无边框窗口里可拖动应用：

| 操作         | 实现                                                                                             |
| ------------ | ------------------------------------------------------------------------------------------------ |
| 任务标题     | 单行省略。顶栏是窗口拖拽区，按住可移动应用                                                       |
| 强状态       | 只在运行、等待审批、失败时显示；空闲和完成不占顶栏                                                |
| 打开结果     | 切换结果工作区（`⌘I`）；无结果时可隐藏。按钮本身 `no-drag`，不拦截窗口拖动                         |
| 更多操作     | 右上角 `⋯` 展开菜单：设置目标（已有目标时为“目标与预算”）、分叉、旁聊；沿用原有操作，选择后关闭菜单。支持方向键、Esc 和点击外部关闭；按钮与浮层均为 `no-drag` |

对话内搜索由 `⌘F` 唤出临时搜索条。分享、历史提问等链路接通后进入任务菜单，不为未接通能力保留常驻图标。

任务菜单还可承载以下已接通设置：

| 任务级设置       | 实现                                                          |
| ---------------- | ------------------------------------------------------------- |
| 切换工作模式     | 下一次 `turn/start` 生效；**不追溯已发生的回合**              |
| 切换权限 profile | `turn/start.permissions`（F5：不与 `sandboxPolicy` 同传）     |
| 切换模型         | `turn/start.model`                                            |
| 任务是否贡献记忆 | `/memories` 弹窗调用 `thread/memoryMode/set` (exp)；全局控制在「设置 → 个性化」 |
| 新任务读取记忆 | 通过 `/memories` 弹窗在发送前选择跟随全局 / 读取 / 不读取；经 `thread/start.config` 生效，宿主保存并在恢复、分叉时重放；已加载任务不能热切换，也不撤回历史 |
| 设定预算         | `thread/goal/set` 的 `tokenBudget`（Q11，10 §5）              |
| 压缩上下文       | `thread/compact/start`，并在流里插入 `ContextCompaction` item |
| 回滚 / 撤销      | `thread/rollback` / `thread/revert`（§6.3）                   |

## 5. 消息流：19 类 Item 的渲染规范

内核的 `ThreadItem` 共 19 个变体（`v2/item.rs:237-414`，README F13）。对话区不是"消息 + 工具"两类，必须逐类给出呈现方式，否则会出现大量"未知事件"占位。

### 5.1 通用规则

- **内容列 768**，用户消息右对齐块（最大宽 640，`--bg-sunken` 底，`--r-lg`），agent 输出**左对齐无气泡**（长文可读性优先）。宽产物可到 896。
- 每个 item 有稳定 `id`，流式增量按 id 合并（`item/agentMessage/delta`、`item/plan/delta`、`item/commandExecution/outputDelta` 等）。
- 助手进度说明与最终回复始终直接铺开，按事件顺序显示，不因后续工具到达而移动。仅同一回合中相邻的操作条目归并为操作组；用户消息、助手说明、推理、计划、文件变更、产物与未知事件切断分组。
- 操作组默认折叠，摘要按真实动作显示「已读取文件 · 运行命令 · 搜索网页」等；运行中的当前动作在摘要下单独可见。用户展开后保持选择，命令输出与工具 JSON 仍二次折叠；失败操作在摘要中可见，但不把单次失败当作整个回合失败。
- 每个回合在首条助手内容前显示处理耗时与分隔线。运行时按开始时间更新，终态使用回合 durationMs；不累加并行操作耗时。历史通过协议恢复回合元数据，缺失时间时不编造数字。停止、失败、断线分别显示真实状态。
- 推理独立折叠；运行中仅展示协议实际提供的最新文本片段，完成后保留可展开的推理详情。无推理能力的模型不留空壳。
- 历史恢复以内核通过协议返回的已保存条目为准。中断发生在文本条目完成前时，尚未保存的字符增量可能不在刷新后的历史中；客户端不建立第二份持久正文仓库。
- 命令详情只展示协议提供的输出；快命令可能在内核开始输出订阅前产生 stdout，此时操作记录没有输出而模型工具结果有正文。没有输出时明确显示「没有可显示的命令输出」，不把命令文本当成 stdout，也不解析模型工具结果补造命令输出。
- 新 item 插入做 150ms 淡入 + 4pt 上移（01 §2.7）；流式文本追加不做动画。
- 自动滚动：仅当用户已在底部时跟随；用户上滑后停止跟随并在右下角显示「↓ 有新内容」按钮。

助手的 `[[cite:web_…]]` 标记只在已有的 Markdown 清洗后变成引用链接，取实际工具结果里的

### 5.4 排队追问（清单 §5.1）

`thread/queue/*`（exp，FIFO、可重排、可编辑）。执行中输入并发送 → 入队而非报错。UI：

- Composer 上方出现「排队中 (2)」折叠区，每项可编辑（`thread/queue/update`）、删除（`delete`）、拖拽重排（`reorder`）。
- 队列变更由 `thread/queue/changed` 通知驱动。
- 当前回合结束后自动出队执行（`thread/queue/start`）。

### 5.5 中断与转向（清单 §5.6）

**2026-10-12 布局补齐**：持续目标摘要最多两行，完整目标可通过悬停及目标设置面板查看；右侧状态不收缩、不折行。只有一个文本段的计划进度正常换行，不套用状态标签的单行限制。


**2026-10-06 长任务与失败恢复**：目标与状态常驻任务顶部，计划显示已完成步骤和当前步骤；没有计划时只显示实际执行状态，不编造百分比或预计完成时间。无 Token 预算的目标也显示，目标状态使用中文。失败和中断任务提供「继续任务」：原任务追加检查历史/产物并完成剩余步骤的指令，使用任务已有模型、审批档和固定工作目录。启动期间按钮禁用，重复点击不追加第二个回合；已有草稿保留。内核重启后的历史快照清除失效流式状态及断线重试提示，不把中断操作标成成功。正常失败卡的原始错误详情和模型设置入口继续保留。

| 动作           | 协议                           | UI                                                          |
| -------------- | ------------------------------ | ----------------------------------------------------------- |
| 中断           | `turn/interrupt`               | 独立“停止”按钮（03 §4.6）；`⌘.` 或 `⎋`                      |
| 中断后补充     | `thread/resume` + `turn/start` | 中断后流里插入分隔线「已中断」+ Composer 聚焦               |
| 不中断直接转向 | `turn/steer`                   | Composer 提供“排队发送 / 立即插话”；仅本次发送走 `steer`       |

运行中保留独立的发送与“停止”按钮。Composer 下方以互斥选项显示“排队发送 / 立即插话”，默认“排队发送”；发送按钮文案跟随本次选择，Enter 与点击发送语义一致，Shift+Enter 换行。停止不发送草稿，Esc / ⌘. 仍可中断。

插话只对本次成功发送生效；成功后恢复“排队发送”。发送失败保留草稿、附件和本次选择供重试；切换任务、回到新任务或当前任务结束运行时清除插话选择，不存为全局偏好。发送请求在途时禁用发送和方式选择，停止仍可用。旧任务迟到的发送回执不能清空当前草稿或改变当前选择。

发送反馈以宿主确认的实际结果为准，在 Composer 下方的可读屏状态区显示：排队为“等待当前任务完成”，插话为“已发送，正在调整方向”。插话请求被降级为排队时显示排队反馈及具体原因，不显示插话成功；没有活动回合时提示“当前没有可插话的回合，这条输入已改为排队。”。回执仅证明内核接收，不承诺模型已执行新要求；插话不撤销已有输出或动作，也不保证立即取消在途工具。切换任务或结束运行时清除旧反馈。

**当前队列实现**：内核持久队列由 queue extension 在任务空闲时自动出队，桌面不在完成通知中重复启动；用户明确继续时才手动启动。实验队列不可用时使用本机持久队列，同样返回排队结果；本机队列仅在后续 `turn/start` 成功后移除，失败保留输入。页面支持队列编辑、上下调序及删除。

任务顶栏不常驻展示重命名、分叉、归档、删除；分叉与旁聊进入 `⋯` 菜单，归档和删除走侧栏任务菜单。时间线不展示消息级复制、重试与分叉，其余动作仍按“未接通不展示”处理。

### 5.6 子任务

父任务流里以 `SubAgentActivity` 折叠卡呈现（§5.2 #13）。点击后进入子 thread 的完整 item 流（`thread/read` / `thread/items/list`），但这条时间线是**只读视图**：用户不能用普通 `turn/start` / `turn/steer` 直接改写子代理。子视图中的“继续交代”由桌面宿主送回根任务，再由根代理通过 `followup_task`（空闲子代理）或 `send_message`（运行中子代理）路由；嵌套子代理也必须逐级追溯到根任务，不能只发给直接父 thread。谱系查询用 `thread/list?ancestorThreadId=` (exp)。并发上限与预算闸门在 10 §5。

#### 5.6.1 上下文与文件的共享边界

对齐现行 ChatGPT/Codex 多代理语义时，必须把两种“共享”分开：

- **工作区共享**：同一任务树里的代理看到同一个 checkout / worktree，文件修改立即互相可见；并发写同一文件仍可能冲突，不等于事务式协作。
- **上下文按代理隔离**：每个代理拥有独立对话历史和独立压缩周期；`spawn_agent` 的 `fork_turns` 只在创建时复制全部、零条或最近 N 轮，不会在创建后持续同步“共同记忆”。
- **后续信息靠显式消息**：父子或兄弟代理通过 `send_message` 传递运行中补充，通过 `followup_task` 重新唤醒已空闲代理；最终结果回到发起它的父代理，再由根代理汇总给用户。
- **谱系可见**：UI 与本机投影至少保留 canonical agent path、sender、全部 recipients、消息种类与状态；不能只显示角色昵称，也不能把多接收者压成一个 `childThreadId`。

内核配置必须显式启用 `[features.multi_agent_v2]`，并把 `non_code_mode_only = false`，使上述六个 V2 协作动作在 Craft / Plan / Ask 中保持同一语义。首次安装写模板；已有安装由宿主做幂等、定向迁移，不覆盖网关、权限等企业配置。

- 动作：本机逐文件撤销恢复实际磁盘字节，按快照版本、后态哈希、运行状态及目录范围核对；原生会话回滚仅改变对话。两者都必须二次确认并说明范围，缺少完整副本时不显示磁盘撤销按钮。

### 6.4 浏览器（清单 §6.4）

总纲 §3.3 已判定 `BrowserUseConfig` 只是权限策略层，真实浏览器需外部 MCP server（Q9 保留的唯一连接器）。

- UI：地址栏 + 刷新 + 前进后退 + 「在系统浏览器打开」+ 视口尺寸预设。
- 内容渲染在**独立 origin 的 WebView**，与应用主 origin 隔离（R5）。
- 用途：预览 agent 起的本地 web 应用（`http://localhost:*`）、预览 HTML 产物、查看搜索结果页。
- **不做**：让 agent 通过这个 WebView 操作页面 —— agent 侧的浏览器操作走 browser MCP server 的 CDP 通道，两者是不同的东西，UI 上不混在一起。

## 7. Visualizer（总纲 §6.10）

agent 用受控 fence 输出，前端识别渲染。**这是 R5（XSS）的落点，规则不可放宽**：

| Fence                | 渲染               | 安全                                                                                                                                                                                      |
| -------------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ` ```mermaid `       | mermaid → SVG      | 库本地打包；`securityLevel: 'strict'`；渲染结果作为 SVG 插入前过一遍白名单清洗（禁 `<script>`、`<foreignObject>`、事件属性）                                                              |
| ` ```evowork-chart ` | JSON spec → 图表库 | **spec 先过 JSON Schema 校验**，非法字段拒绝渲染并显示原始 JSON；不允许 spec 内含函数/表达式字符串                                                                                        |
| ` ```html `          | 沙箱 iframe        | **独立 origin**（`sandbox="allow-scripts"` 但**不给** `allow-same-origin`）+ 严格 CSP（`default-src 'none'; style-src 'unsafe-inline'; img-src data:`）+ 禁外链 + 高度上限 600 后内部滚动 |
| 其他 fence           | 代码块             | 高亮 + 复制，不执行                                                                                                                                                                       |

三类都在渲染框右上角提供“查看源码”与“保存为文件”。mermaid 与 chart 的配色从 01 §2 的浅色 token 注入；HTML iframe 使用自身受控样式，不承担应用主题切换。

**多图叙事**（清单 §11）：一条 `AgentMessage` 内多个 fence 按顺序纵向排列，不做轮播 —— 对话流里的横向轮播会丢失上下文。

### 运行中投递的故障与竞态契约（2026-10-18）

每次发送带独立 submissionId，与任务草稿环境 id 分开。同一内容重试沿用发送身份；确认已接受后不重复投递。回执超时先通过公开队列/历史接口按 clientUserMessageId/clientId 核对；仍无法确认时显示“发送结果尚未确认”，保留草稿、附件和方式选择，只允许原身份核对，不盲目重发。明确拒绝才可再次投递。回执去重及队列的重启恢复见下文。

插话遇到原回合已完成或已切换的明确拒绝时，改走原生队列并说明原因；其他拒绝不得伪装成成功。若此时原生队列也不可用，本机队列确认原回合已经结束后直接启动新回合，提示“原回合已结束，这条输入已开始执行”，不再等待不存在的完成事件。队列刷新失败不改变已经确认的投递结果。发送处理中防止重复 Enter/点击，切任务后迟到回执不得清除新任务草稿或跳回旧任务。

停止保留队列但暂停自动续跑；本机降级队列与原生队列一致。空闲且队列非空时提供“继续队列”，只有用户明确继续才恢复。自然完成继续自动出队，中断和失败不触发本机队列出队。

### 重启恢复（2026-10-18）

发送意图、接受回执、待发内容及停止标记采用本机权威持久化。恢复的本机队列等待“继续队列”，停止后的原生队列在加载任务前接管为本机暂停队列。跨进程未知发送只核对，不自动重投；同内容重试保留原提交身份，草稿与附件恢复。删除任务同时清理对应本机队列、暂停标记与回执。详细边界见总纲的“运行中投递重启恢复补充”。
