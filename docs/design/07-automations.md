# 07 · 自动化（Automations）

> 上游：[总纲 D5 / §6.9](../evowork-on-codex-design.md)· Q1=A · Q8 · Q15 · R9 · [清单 §7](../agent-platform-feature-list.md)
> 截图未覆盖此页。总纲已定数据模型与失败语义，本文补**界面、文案与真实体验**——R9 与总纲 §10.2 第 3 条都指向"用户看到的文案是否与实际一致"，那是这个模块的主要风险，而它只能在设计里解决。

## 1. 这个模块的设计难点不是功能，是诚实

Q1=A 决定了调度跑在用户机器上：**关机就不跑，休眠可能漏跑，只有绑定的那台设备会跑**。总纲 D5 把它归为"可靠性从服务端保证降级为尽力而为"，并要求「前端必须如实展示，不得让用户误以为是云端级 SLA」。

因此本模块每个界面元素都要回答用户的一个疑问：

| 用户会问                   | 界面必须能直接回答                       | 落点 |
| -------------------------- | ---------------------------------------- | ---- |
| 它下次什么时候跑？         | 下次执行时间（含时区）                   | §3.2 |
| 昨晚跑了吗？               | 执行历史 + **跳过原因**                  | §5   |
| 我关机了会怎样？           | misfire 策略的**人话说明**，在配置时就说 | §4.3 |
| 为什么它停了？             | 连续失败 3 次自动暂停的显式通知          | §5.4 |
| 为什么在这台电脑上是灰的？ | 设备绑定说明 + 迁移入口                  | §6   |

**反例（不允许）**：显示"每天 9:00 执行"却不说明机器关机时不执行；显示"上次执行：失败"却不说是模型报错还是机器离线；把 `MISSED` 混进"失败"里统计。

## 2. 页面结构

### 2.1 列表页 `/automations`（两栏 · 目录式）

```
标题栏带 │ 自动化                    ····· [🔍 搜索] [☰ 全部状态 ▾] [＋ 新建自动化]
─────────┴─────────────────────────────────────────────────────────────
内容列 800
  ├ 本机运行中的自动化（本设备）
  │   AutomationCard × N
  ├ 在其他设备上运行（只读）              ← Q15；折叠，默认展开
  │   AutomationCard（锁态）× N
  └ 已暂停 / 已过期
      AutomationCard（灰态）× N
```

**分组按"在哪台机器上跑"而不是按状态**——这是 Q1=A 下用户最需要先分清的一层。状态在卡内呈现。

### 2.2 AutomationCard

```
┌────────────────────────────────────────────────────────┐
│ ⏰ 每周一 9:00 生成上周周报            [Badge 运行中] [⋯] │
│ 📁 ~/work/weekly  ·  🤖 deepseek-chat  ·  💰 上限 200k  │
│ 下次执行：2026-09-07 09:00 (GMT+8) · 还有 3 天           │
│ 上次执行：2026-09-01 09:02 成功 · 用了 46k tokens        │
└────────────────────────────────────────────────────────┘
```

- 第 1 行：名称（用户命名，或从 prompt 自动摘要）+ 状态 Badge + 操作菜单。
- 第 2 行：工作空间（多个时显示「+2」）· 模型 · 预算上限。
- 第 3–4 行：**下次执行 / 上次执行是卡片的核心信息**，不折叠、不省略、带时区。
- 状态 Badge：运行中（ACTIVE）· 执行中（有 in-flight run）· 已暂停（PAUSED）· 已过期（超过 `valid_until`）· 其他设备（只读锁态，01 §6.3）。
- 异常态覆盖第 3 行：`--warning` 底 + 「上次触发被跳过：当时电脑处于关机状态」（§5.3 的文案表）。

### 2.3 详情页 `/automations/:id`

上半：配置摘要（可就地编辑，§3–4）。下半：执行历史表（§5）。右上：启用/暂停开关、立即运行一次、删除。

## 3. 创建流程

### 3.1 双入口

| 入口               | 场景                                                                                                                                                                      |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 「＋ 新建自动化」  | 从零配置，走 §3.2 的表单                                                                                                                                                  |
| **从任务转自动化** | 在任务工作台的任务菜单里「设为定时任务」——把该任务的 prompt / 工作空间 / 模型 / 权限 / 场景直接带过来。**这是主路径**：用户先手动跑通一次，再定时化，成功率远高于凭空配置 |

第二个入口是产品判断：清单 §7 说"用平实语言描述任务内容和执行时间即可"，但一个从没跑过的 prompt 定时跑，失败会以"连续 3 次自动暂停"的形式在三天后才被发现。因此表单里内置**「先试跑一次」**（§3.4）。

### 3.2 表单字段（对齐总纲 §6.9 数据模型）

| 字段                                | 控件                                 | 默认                | 说明                                                                                   |
| ----------------------------------- | ------------------------------------ | ------------------- | -------------------------------------------------------------------------------------- |
| 名称                                | 输入                                 | 从 prompt 自动摘要  | —                                                                                      |
| 任务描述 `prompt`                   | 多行（同 Composer，支持 `@` 与 `/`） | —                   | 支持引用技能与资料库条目                                                               |
| 工作空间 `workspaces[]`             | 多选                                 | 当前空间            | 本机绝对路径；**必须存在**才能保存                                                     |
| 触发 `schedule`                     | 见 §3.3                              | —                   | cron 或 `once@timestamp`                                                               |
| 时区 `timezone`                     | 下拉                                 | 系统时区            | 显式存储，不依赖运行时系统设置（跨时区出差不改变触发时刻）                             |
| 生效期 `valid_from` / `valid_until` | 日期区间                             | 立即 / 无限期       | 清单 §7 要求                                                                           |
| 模型 / 权限 / 模式                  | 同 Composer 三个 `InlineSelect`      | 场景默认            | 复用 03 §4.5                                                                           |
| 预算                                | 数字 + 单位                          | 场景默认            | `ThreadGoal.budget`（Q11）；**定时任务必须有硬预算**，否则一个失控循环会在夜里烧完配额 |
| 错过补偿 `misfire_policy`           | 三选一                               | `FIRE_ONCE_ON_WAKE` | 见 §4.3                                                                                |
| 补偿窗口 `catchup_window`           | 下拉                                 | 24h                 | —                                                                                      |
| 允许唤醒电脑 `wake_system`          | 开关                                 | **关**              | 见 §4.4                                                                                |
| 并发 `concurrency_policy`           | —                                    | 固定 `SKIP`         | Q8 已定为固定值，**不做成选项**                                                        |
| 重试                                | —                                    | 固定不重试          | Q8 已定                                                                                |

**不做成选项的两项要在界面上写明白**，而不是隐藏：表单底部一行 `caption`：「上一次还没跑完就到了下次时间，会跳过这一次；执行失败不会自动重试，连续失败 3 次会自动暂停并通知你。」

### 3.3 触发编辑器

三档递进，避免让普通用户面对 cron 表达式：

```
① 常用          [ 每天 ] [ 每周 ] [ 每月 ] [ 每年 ] [ 一次 ]
                 每周  [周一▾] [09:00▾]
② 自然语言       输入「每个工作日下午六点」→ 解析为 cron + 回显人话确认
③ 高级          cron 表达式 + 实时校验 + 「未来 5 次触发时间」预览
```

- 第 ② 档是清单 §7「自然语言配置」的落点。解析在**本机完成**（规则 + 词表，不调模型），失败则回落到第 ① 档并提示。理由：把"设定一个每天跑的任务"这件事的可靠性押在一次模型调用上不合适。
- **「未来 5 次触发时间」预览是三档共有的**，且必须显示时区。这是防止配错的最有效手段。

### 3.4 保存前的试跑

「保存并立即试跑一次」（默认勾选）。试跑 = 用同样的参数跑一次真实执行，结果记为 `automation_run` 且标记 `trigger = MANUAL_TEST`。试跑失败时不阻止保存，但把卡片状态标为「未验证」（`--warning`），提示"这个任务还没成功执行过"。

## 4. Q1=A 的三个特有问题的界面落点

### 4.1 设备绑定（Q15）

创建时自动绑定当前设备（`device_id`），表单底部固定一行：「将在这台电脑（MacBook-Pro-J）上执行。其他电脑上可以看到它，但不会重复执行。」

### 4.2 关机/休眠的预期管理

触发编辑器下方常驻 `--info` 提示条（**不可关闭**）：

> 定时任务在这台电脑上运行。电脑关机或睡眠时不会执行，重新开机后按下方「错过补偿」的设置处理。

这句话必须出现在**配置时**而不是只在事后解释，否则用户的心智模型从第一天就是错的（R9）。

### 4.3 错过补偿（`misfire_policy`）的人话

| 值                          | 界面文案           | 副说明                                                |
| --------------------------- | ------------------ | ----------------------------------------------------- |
| `FIRE_ONCE_ON_WAKE`（默认） | **开机后补跑一次** | 无论错过几次，只补最近的一次                          |
| `FIRE_ALL`                  | 逐次补齐           | 错过 3 次就跑 3 次，适合"每次都要留痕"的任务          |
| `DROP`                      | 不补跑             | 错过就算了，适合时效性强的任务（如"每天 9 点发早报"） |

三项都附一句「只补最近 24 小时内错过的触发」（`catchup_window`）。选 `FIRE_ALL` 时额外警告：「如果电脑关机较久，可能会连续执行多次并消耗较多额度。」

### 4.4 唤醒电脑（`wake_system`）

开关默认关。开启时的说明必须给出平台差异与限制（总纲 D5）：

> 开启后 EvoWork 会请求系统在触发时唤醒电脑（macOS / Windows / Linux 各自的定时唤醒机制）。**合盖、断电或系统禁用唤醒时仍然不会执行。**

不承诺"一定能唤醒"——这是操作系统决定的。

## 5. 执行历史

### 5.1 表格（`DataTable`，01 §5.28）

| 列       | 内容                                                     |
| -------- | -------------------------------------------------------- |
| 触发时间 | `fire_time`，带时区；手动/试跑触发加图标区分             |
| 状态     | Badge：成功 / 失败 / **跳过** / **漏跑** / 执行中        |
| 结果     | 成功→产物数与「查看任务」；失败→错误摘要；跳过/漏跑→原因 |
| 耗时     | —                                                        |
| 用量     | tokens + 估算成本                                        |

**「跳过」与「漏跑」必须与「失败」分列统计**，否则用户会以为任务本身有问题。列表顶部给出近 30 次的统计条：`成功 24 · 失败 2 · 跳过 3 · 漏跑 1`。

### 5.2 状态与数据模型的对应

总纲 §6.9 的 `automation_run.status` = `RUNNING | SUCCEEDED | FAILED | SKIPPED | MISSED`，`skip_reason` = `CONCURRENCY | MACHINE_OFFLINE | OUT_OF_WINDOW | QUOTA`。界面映射：

| status / skip_reason         | Badge   | 文案                      |
| ---------------------------- | ------- | ------------------------- |
| `SUCCEEDED`                  | success | 成功                      |
| `FAILED`                     | danger  | 失败 · <错误分类>         |
| `SKIPPED` + `CONCURRENCY`    | warning | 跳过 · 上一次还在执行中   |
| `SKIPPED` + `QUOTA`          | warning | 跳过 · 额度不足           |
| `SKIPPED` + `OUT_OF_WINDOW`  | neutral | 跳过 · 不在生效期内       |
| `MISSED` + `MACHINE_OFFLINE` | neutral | 漏跑 · 当时电脑关机或睡眠 |
| `RUNNING`                    | info    | 执行中 · 「查看」         |

### 5.3 文案一致性（总纲 §10.2 第 3 条要在 M0 拿结论的那一项）

三处文案说的必须是同一件事，任何一处对不上就是 bug：

1. **配置时**的预期说明（§4.2 / §4.3）
2. **通知**（02 §5.1 的"触发被跳过"）
3. **历史记录**里的原因（§5.2）

举例：`misfire_policy = FIRE_ONCE_ON_WAKE`、关机一夜错过 1 次、开机后补跑 → 历史里应出现**两条**记录：一条 `MISSED / MACHINE_OFFLINE`（原定 9:00）+ 一条 `SUCCEEDED` 且标注「补跑（原定 09-03 09:00）」。**不能只留补跑那一条** —— 否则用户永远不知道自己漏了。这条要求直接决定 scheduler 的落库逻辑（09 §6），不只是 UI。

### 5.4 自动暂停（Q8）

`consecutive_failures` 达 3 → `status = PAUSED` + 通知。界面：

- 卡片转灰 + Badge「已自动暂停」+ 第 3 行替换为「连续失败 3 次后已自动暂停 · 最后一次错误：<摘要>」。
- 详情页顶部 `--danger` 条 + 「查看最近 3 次失败」+ 「恢复运行」（恢复时清零计数）。
- 通知文案给出下一步：「自动化「周报」已暂停。最近 3 次都因为模型调用失败。查看详情 ›」

## 6. 多设备（Q15 的界面落点）

### 6.1 其他设备上的自动化

`AutomationCard` 只读锁态（01 §6.3：正常色 + 锁图标 + tooltip）：

```
🔒 每天 8:30 汇总昨日数据             [Badge 其他设备]
   在 Windows-Office 上运行 · 该设备最后在线 9 天前
   [迁移到本机]
```

- 只读态下所有编辑动作禁用（禁用要给原因，01 §6.3）。
- 绑定设备离线 > 7 天：卡片转 `--warning` + 「该设备已离线 9 天，任务可能一直没有执行」+ 迁移按钮变主按钮。这就是 Q15 的"提示迁移"。

### 6.2 迁移到本机

严格按总纲 §6.9 的四条约束实现，每条都有对应的 UI：

| 约束                                            | UI                                                                                         |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 排他操作，用云端定义做乐观锁                    | 迁移中显示进度；并发迁移失败时提示「另一台设备正在认领这个任务，请稍后重试」               |
| **重置 misfire 基准为迁移时刻**                 | 确认模态明写：「迁移后不会补跑迁移之前错过的触发。」（否则新设备一上线就补出一堆历史执行） |
| 工作空间路径在新设备不存在 → 必须失败并要求重选 | 迁移前校验路径；缺失时弹出路径重选步骤，**不允许静默改路径**，也不允许"先迁移后修"         |
| 迁移是改 `device_id`                            | 成功后卡片移入"本机"分组，原设备端下次同步后转为只读                                       |

### 6.3 离线与同步

- automation **定义**备份到云端供多设备可见（D5），**执行历史与产物不同步**（D6）。
- 详情页历史表顶部一行 `caption`：「执行历史保存在执行它的那台电脑上。这里显示的是本机记录。」
- 云端不可达时：本机自动化照常触发（调度完全本地），列表页顶部 `--warning` 条「暂时无法同步到云端，其他设备上看到的信息可能不是最新的」——**不影响执行，只影响可见性**，文案要区分清楚。

## 7. 空态与异常

| 情况               | 表现                                                                                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 无自动化           | 空态：「还没有定时任务 / 让 EvoWork 每周一自动生成周报，或每天汇总数据」+ 「新建自动化」+ 2 个示例模板                                               |
| 工作空间路径失效   | 卡片 `--danger` + 「工作空间不存在，任务无法执行」+ 「重新指定」；同时自动置 PAUSED（避免持续失败刷计数）                                            |
| 额度不足           | 卡片 `--warning` + 触发时记 `SKIPPED / QUOTA`；通知一次（不每次都通知）                                                                              |
| 模型/网关不可用    | 记 `FAILED`，错误分类为「模型服务不可用」，计入 `consecutive_failures`                                                                               |
| 系统时区变更       | 因为存了显式 `timezone`，触发时刻不变；检测到系统时区变化时提示一次：「系统时区已变化，你的定时任务仍按 GMT+8 执行，需要调整吗？」                   |
| 夏令时             | cron 按存储时区解析；跨夏令时切换的当天，重复的小时只触发一次、缺失的小时按 misfire 处理，并在历史里注明                                             |
| 电脑在执行中被关机 | 下次启动时把 `RUNNING` 且超时的 run 标为 `FAILED`，错误分类「执行被中断（电脑关机）」，**并且不计入 `consecutive_failures`** —— 这不是任务本身的问题 |

最后一条是设计判断：把环境原因造成的失败计入自动暂停计数，会让笔记本用户的自动化三天内全部被暂停。**只有任务自身失败（模型错误、脚本错误、审批超时）才计数。**

## 8. 与总纲的差异登记

| #   | 内容                                                                                                                                      | 性质                                                                      |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 1   | `automation_run` 需新增 `trigger` 字段（`SCHEDULED` / `MANUAL` / `MANUAL_TEST` / `CATCHUP`）与 `original_fire_time`（补跑时指向原定时刻） | **数据模型增量**，由 §5.3 的文案一致性要求推出；建议回写总纲 §6.9         |
| 2   | 环境原因失败不计入 `consecutive_failures`                                                                                                 | **对 Q8 的细化**（Q8 只说"失败 3 次暂停"，未区分失败来源）；建议回写      |
| 3   | 定时任务强制要求硬预算                                                                                                                    | **对 Q11 的收紧**（Q11 说单任务硬预算，此处要求自动化不得不设）；建议回写 |
| 4   | 自然语言时间解析在本机用规则实现，不调模型                                                                                                | 实现选择，无需回写                                                        |
