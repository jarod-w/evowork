## 零、第一原则：零丢弃

POC 最常见的死法有两种，方向相反：

- **为 POC 而 POC**：写一堆演示专用代码，客户点头之后全部推倒，等于白干一个月，还额外背上"新旧两套并行维护"的代价
- **借 POC 之名做全量**：把 Phase 3 的东西都做上，客户等不到，POC 失败

本文所有取舍服从下面这条判据，它同时避开两个方向：

> ### **允许实现简陋，不允许调用点错位。**
>
> 未来要替换的必须是某个组件的**实现**，而不是它的**调用方**。
> 一项工作如果将来替换时需要回头改调用它的代码，那它就是一次性投入——POC 期就不要那样做。

推论：**POC 交付物 = 产品主干上的一个 tag，不是一个分支。** 不存在"POC 分支"、"demo 模式"、"演示开关"这类东西。

### 0.1 六条红线（越过任何一条，就是在做一次性工程）

| # | 红线 | 越过的代价 |
|---|------|-----------|
| 1 | **Agent Loop 写进 UI 进程** | 技术路线第九节点名的头号坑：第 6 个月一次数人月重写，且重写期间出不了新功能 |
| 2 | **工具调用绕过 Effect Gateway**（"先接上跑起来，Gateway 以后补"） | 补的时候要逐个工具回炉；接到第 30 个工具时会静默漏掉一项治理检查，而且你不会发现 |
| 3 | **Run Log 字段"先存个大概，以后补"** | 半年后旧任务不可回放，审计价值归零；且早期 Log 是 Phase 4 自蒸馏的原料，不存就永远补不回来 |
| 4 | **内核里读时钟 / 随机数 / 环境变量** | 回放结果与原始执行不一致，回放不能作为取证依据——且这条通常在半年后才被发现 |
| 5 | **为演示铺 mock 数据、预置答案、演示专用页面** | 演示当天最省事，客户拿到手当天崩；且这部分代码 100% 是要删的 |
| 6 | **把客户的业务口径写进代码或提示词** | 换一个客户就要改一遍代码。正确承载方式见 0.3 |

### 0.2 允许简陋的地方（白名单——不要在这些地方过度投入）

红线之外，POC 期**应当**尽量糊。以下每一项都只糊实现，接口即最终接口：

| 组件 | POC 期做到 | 将来怎么升级 |
|---|---|---|
| 策略引擎 | 规则硬编码 | 换成 Cedar / OPA，**只换 Gateway 里策略钩子的实现**，调用点不动 |
| 记忆 | 单工作空间，ACL / provenance 字段留空但**必须存在** | 填上字段值即得分层记忆与权限隔离 |
| 审计防篡改 | 先不做 hash chain，但 Log 必须 append-only | 追加 hash 列 + 外部锚定 |
| 执行面 | 只做本地沙箱一种实现（**实现可直接复用开源件，见 4.11**） | 组织内 Runner / 云沙箱是同一接口的另两种实现 |
| 密钥 | 本地 keychain 最简实现 | 换托管服务，Agent 上下文里永不出现明文这条从第一天就成立 |
| UI | 功能少、样式糙 | 允许难看，不允许只有演示路径能走通 |
| 沙箱 | 平台原生原语的最简配置 | 逐步收紧策略 |

### 0.3 客户定制的吸收机制

POC 期必然出现客户特化需求。**每一条都必须被某个产品机制吸收，而不是变成代码分支**——这是零丢弃能否成立的实操关键：

| POC 期必然出现的定制 | 一次性做法（禁止） | 产品机制承载（正确） |
|---|---|---|
| 客户的报表口径、审批流、命名规范、行业禁忌 | 写进 prompt / if 分支 | **组织私有流程库**——以数据和文件存在，不进代码 |
| 客户特有的系统接入 | 写一个专用 adapter | **MCP Server**（本地或远端），产品侧零特化 |
| 客户想要的固定执行流程 | 手写编排脚本 | POC 期先让 Agent 自己做；确实稳定后才固化为 workflow-as-code（P1，POC 期尽量不做） |
| 客户的高危操作口径 | 散落的 if 判断 | 硬编码规则，但**放在 Gateway 的策略钩子里**——将来换 policy-as-code 只换实现 |
| 演示环境凭据 | 明文配置 | 密钥托管的最简实现，接口即产品接口 |
| 演示要好看 | 演示专用页面 | 就用产品页面，功能少但真实 |

> 一句话检验：**客户 A 的全部定制，能不能不改一行代码换成客户 B？** 不能，就说明有东西写错地方了。

## 一、POC 到底在被评估什么

不是"功能多不多"。企业 POC 复盘会上被问倒的永远是这三句：

| 客户的问题 | 对应能力 |
|---|---|
| **我的数据去哪了？** | 本地沙箱执行 + 网络出口白名单（默认拒绝、全量记账） |
| **它干错了我怎么查、怎么举证？** | Run Log + 执行回放 + 产物 diff |
| **这东西一个月烧我多少钱？** | 成本归因 + 预算闸门 |

这三项在功能清单里都不算"亮点功能"，但**缺任何一项，采购流程都过不去**。它们同时正好是 EVOWORK 相对同类产品的真实差异点——所以 POC 该演的就是它们。

本客户（玩具行业 · 用友财务）让第一条的权重再翻一倍：**财务明细上云是客户最抗拒的一件事**，「数据不出本机」在这里不是加分项，是准入条件。

## 二、功能清单

### A 类 · 必须演示（就这些，不要再加）

| # | 功能 | 为什么 POC 必须有 | 留存去向 |
|---|---|---|---|
| 1 | **单 Agent 任务闭环**：自然语言 → 规划 → 工具调用 → 产物 | 基本盘 | 事件溯源内核（地基 A），全生命周期复用 |
| 2 | **本地沙箱执行**：文件读写 / Bash / 托管 Python·Node | 「数据不出本机」是可**验证**的承诺，放权第一级台阶 | 执行面（地基 D）的第一种实现，接口即最终接口 |
| 3 | **执行过程可折叠 + 产物区**（预览 / diff / 内置浏览器） | 早期 Agent 不可靠，人必须能随时看进去 | Run Log 的时间线视图，回放 UI 的前身 |
| 4 | **干运行（dry-run）+ 影响预估** | 现场最有说服力的一幕：先说要动哪些文件，人点了才动 | Gateway 的一种**执行策略**（不是每个工具各写的预览模式） |
| 5 | **高危操作确认（异步，不阻塞执行）** | 直接回答"会不会失控" | `approval.pending` / `approval.granted` 事件，异步审批的最小形态 |
| 6 | **执行历史 + trace 回放** | 回答"出事能不能查" | Run Log 的查询视图，零额外存储 |
| 7 | **成本归因**（按任务/人给出 token·时长·费用） | 采购必问 | `cost.charged` 事件聚合，四维归因的第一维 |
| 8 | **定时 + 1 个 webhook 触发，UI 关了继续跑** | 唯一能演出"它是同事不是工具"的一幕，「客户端即运行时」的产品演不了 | 触发器调度 + daemon 边界，Phase 1 直接复用 |
| 9 | **MCP 接入用友（只读）+ 一个外发通道**（邮件或企业 IM） | 接不上客户自己的系统，POC 就是玩具；财务数据正是这个客户的价值密度所在 | 产品标准接入方式，主干里零行「用友」，见 4.1 |
| 10 | **网络出口白名单** | 安全评审必问；必须在本地 forward proxy 层做，SDK 层拦截当场会被问穿 | Phase 3 DLP 的挂载点；proxy 实现可复用开源件（4.11） |
| 11 | **组织私有流程库·最小版**：账龄分档、客户账期、不催清单、模具费口径、催收话术分级…… | **POC 成败常常只取决于这一项**——通用能力大家都差不多，能不能按客户自己的口径干活才是区别 | 唯一不会被模型吞掉的知识资产；具体清单见 4.6 |
| 12 | **澄清式追问**（带默认选项，一键回答） | 成本极低、感知极强，直接降低"猜错做完再返工" | 🔧 脚手架层，**明确标注可弃**——本身会被模型吞掉，但交互形态留存为 Inbox 的雏形 |
| 13 | **溯源引用·最小版**：报表里每个数字可点回用友的单据 / 科目 / 期间 | 财务人员对 AI 产出的默认假设是"数字是编的"，这是本客户唯一的信任建立机制，见 4.4 | 地基 C 的 `cite` 锚点，本客户直接就有消费方 |

> 第 4、6、7、10 四项在实现上都是 B 类地基的**免费视图**，不是四个独立开发项；第 13 项则是把 B 类的上下文元数据从"暂无消费方"接上消费方，增量只在输出侧的校验与渲染。排期时必须这样算账，否则 Gateway 会被当成"没有用户价值"砍掉——那正是红线 2。

### B 类 · 必须做对但不演（照抄技术路线第九节）

| 项 | POC 阶段做到什么程度 |
|---|---|
| daemon / UI 边界 | 真 IPC，不能是函数调用 |
| Run Log schema | **就用最终 schema**，带版本号；可以只写本地 SQLite、可以还没有回放 UI，字段不能缺 |
| Effect Gateway | 必须存在，**只做记账与审计 + dry-run 开关**，不加策略拦截，零行为影响 |
| 上下文元数据 | 每段带 `source / trust / cite`。**本客户已有消费方**（A 类第 13 项），用友取数标 `org_trusted`，客户邮件/外部对账单标 `untrusted` |
| 内核确定性 | 禁读时钟 / 随机数 / 环境变量，**构建期静态检查** |

这五项成本合计约一周，是整个方案里**代价最不对称**的部分：现在做多花一周，将来补要花一个季度。向客户汇报时它们不占篇幅，向团队排期时它们不可议价。

### C 类 · POC 明确不做

Agent Fleet 并行、动态组队、对抗式验证、policy-as-code 策略引擎（先硬编码 + 留钩子）、分层记忆与组织记忆（只做单工作空间）、轨迹自蒸馏、技能市场、SSO/RBAC/审批链、DLP、Computer Use、跨设备接管、云端控制面、多模态生成（除非客户场景就是这个）。

被问到时的标准答法是「路线图第 2 / 3 阶段」，**不是**「我们没有」——POC 阶段客户要看的是判断力，不是清单长度。

## 三、两条执行建议（比功能清单更影响成败）

**① 只做一个场景的纵切，宽度砍到底。**
最常见的死法是横向铺开十个场景、每个七成完成度，客户看完觉得"哪个都不敢真用"。正确做法：选客户**自己每周真在做**的一个任务，做到能真交付，其余一律不碰。

**② 用「放权节奏」组织 POC 本身。**
第 1 周只读 + dry-run，只报告"我会做什么"；客户比对几轮认可后，再开授权目录写；最后才碰会外发的动作。**这个节奏本身就是产品核心命题的现场演示**——比任何 PPT 都有效，且失败时成本为零。

## 四、客户场景落地：玩具行业 · 用友对接

第三节是原则，本节是这个客户身上的具体形态。

### 4.1 对接方式：只写 MCP Server，主干里零行「用友」

这是 0.3 吸收机制在本客户身上的落点，也是零丢弃自检第 4 条的直接检验对象：

- 用友接入 = **一个独立的 MCP Server 进程**，不是产品里的一个模块
- 产品主干代码里不允许出现 `yonyou` / `u8` / 财务专有名词
- 换客户到金蝶、SAP、Oracle EBS，只换 MCP Server，产品一行不改

> 违反这条的写法很有诱惑力："先在工具层加个用友 adapter，跑通再说"。跑通那天起，这个客户就长在产品里了。

### 4.2 接口路径：不押版本，先定语义接口

**版本未确认时的正确做法不是猜一个版本，而是让"猜错"不产生代价。** 既然用友接入已被隔离在 MCP Server 里（4.1），那么先固定的应当是**语义接口**——上层 Agent、口径库、报表模板、评测集全部依赖它，版本差异一律在 MCP Server 内部消化：

| MCP tool | 出参（固定 schema） |
|---|---|
| `list_receivables(period)` | 客户、单据号、单据日期、到期日、原币/本币金额、已收、余额 |
| `list_customers()` | 编码、名称、分类、约定账期、业务员 |
| `list_settlements(period)` | 收款与核销记录 |
| `get_period_summary(period)` | 期末应收总额——**评测的对账锚点**（4.7） |

**实现顺序（这才是"容易开发"的答案）：**

| 顺序 | 实现 | 何时做 | 状态 |
|:---:|---|---|---|
| **1** | **实时只读接口** | 立即 | **客户确认只读账号随时可得**，版本随账号一并明确 |
| 2 | 导出文件通道（CSV / Excel） | 顺手做掉 | 离线兜底 + 客户自查入口，成本很低（表格解析本来就要有） |

顺序在此定稿：**账号随时可得，也就没有理由绕道**。第 1 天去拿账号，版本问题同时解决。导出通道降为第 2 项——它仍然要做，但不再是主线。

**但有一条不因此改变：取数必须"取一次即落盘冻结"。** 用友里的历史单据会被红冲、调整、期末结转，今天查 2026-05 和当时财务做表时看到的未必一致。评测集只能跑在冻结快照上（4.7 约束②），实时接口不改变这一点，只是把快照的来源从人工导出换成自动取数。

**只读账号的申请范围要主动收窄**：只申请应收相关的表 / 接口（往来明细、客户档案、收款核销、期末余额），不要全库只读。范围越小批得越快，且它本身就是 POC 现场演「权限只能是发起人权限的子集」的素材。

第 1 项是开发主线，不是降级方案：**任何用友版本都能导出这几张表**，格式差异由 MCP Server 吃掉。它无论最终版本是什么都不会白做，而且大量财务人员本来就习惯先导出再处理。

若确实需要押一个版本先做实时接口，选 **YonSuite / YonBIP**——它是唯一有公开开发者平台与沙箱环境的产品线，标准 REST + OAuth，不依赖客户给环境。但要清楚：**玩具制造企业更可能在用本地部署的 U8+**，押错的话实时接口那部分要重做——这正是先做第 1 项的理由。

其余注意事项：

- POC 期一律**只读**，不申请任何写接口。财务系统的写权限在 POC 阶段基本批不下来，去要只会拖慢审批；而回写用 dry-run 演效果更好且零风险（4.4）
- 玩具制造企业的用友常被二次开发过（BOM、模具、工序），库表未必标准——走导出通道可以完全绕开这个不确定性
- 导出口径必须固定：约定死需要哪几张表、哪些字段、什么查询条件，否则每次导出列都不一样。注意用友导出常为 GBK 编码

### 4.3 原头号风险已消失，M0 只剩一件事

只读账号随时可得，版本随账号明确——原本被列为头号风险的"拿不到数据"整条消失。**M0 因此只剩一个客户侧动作：向财务要历史 3–6 个月的人工成品表**（账龄表与催收清单）。这一件事同时喂饱口径库（4.6）与评测真值（4.7），是当前唯一真正需要客户配合的事，应当第一天就开口要。

导出通道仍然要做，但理由变了：不再是规避审批，而是离线兜底与客户自查入口。

演示时刻 3 现在由常开机器上的定时触发直接兑现（4.8），不再需要绕道文件监听。若还有余力，让 Agent 顺带监听一个共享目录（财务丢进去的临时导出立即被接手）可以多演一项 P0「文件变更事件触发」——**属于加分项，不进 M2 / M3 排期**。

### 4.4 财务场景的两条特化判断

**① 溯源引用在这个客户是刚需，不是地基预留。**
财务人员看 AI 产出的第一反应是"这数字哪来的"。报表里每个数字必须能点回用友的哪张单据、哪个科目、哪个期间。所以把它从 B 类的"暂时没有消费方"提为 A 类第 13 项——这是本客户唯一有效的信任建立机制，其他都是话术。

**② 回写用友只演 dry-run，不真写。**
"能不能直接生成凭证 / 核销单据"是客户必问的下一个问题。正确答法既不是"我们能写"，也不是"我们不做"，而是当场演一遍：给出**将要写入的凭证清单、科目、金额、影响期间**，一条不落，但一条不写。

> 这是 dry-run 这个机制的最佳用例——零风险、高说服力，而且它正好架在客户从 POC 走向采购的那道心理门槛上。

### 4.5 主线场景（已定）：应收账龄 + 回款跟催

**每周一 8:00 自动产出四件东西**，这就是 M2 / M3 的验收物：

| # | 交付物 | 要求 |
|:---:|---|---|
| 1 | **账龄表**（Excel） | 分档金额与结构比，每个数字可点回单据（A 类第 13 项） |
| 2 | **催收清单** | 按优先级排序，含建议动作与话术等级；不催清单里的客户不得出现 |
| 3 | **按业务员分组的跟催任务包** | 客户、金额、账龄、建议动作、话术等级；经企业微信推给对应业务员，**由业务员自己联系客户**，系统不对外发（4.9） |
| 4 | **本次成本** | token / 时长 / 费用，随出表一并推送到企业微信 |

候选对比（留档备查）：

| 候选 | 频率 | 是否需要写 | 口径含量 | 判断 |
|---|---|:---:|:---:|---|
| **B 应收账龄 + 回款跟催清单** | 周 | 纯读 | 高 | ★ **已选** |
| A 经营周报（销售 · 毛利 · 库存） | 周/月 | 纯读 | 高 | 备选，价值稍散 |
| C 呆滞库存与备货预警 | 周 | 纯读 | 中 | 备选，玩具季节性强时价值高 |
| D 费用报销 / 发票预审 | 日 | 需回写 | 中 | **不作主线**，只作 4.4② 的 dry-run 演示点 |

选 B 的五条理由（现场若被问起）：

1. **每周真在做**，且现在是人工导 Excel → 透视 → 手工写邮件，痛点具体
2. **纯读，零写风险**，第一周就能跑通，不卡在权限审批上
3. 玩具行业账期长、大客户集中（商超 / 电商平台 / 授权商 / 外贸），账龄管理是真痛点；且当下正处圣诞订单出货期，应收正在爬坡，数据鲜活
4. **口径极密集**，正好把 4.6 装满——这是护城河唯一的演示机会
5. **四个演示时刻全部自然覆盖，不需要摆拍**：催收邮件"发不发"是真实存在的高危确认点，周一早上自动出表是真实存在的定时需求

### 4.6 口径库该装什么（A 类第 11 项的具体内容）

这些就是"模型不可能先验知道"的东西，一条都不能写进代码或提示词，全部以数据存在：

| 类别 | 具体内容 |
|---|---|
| 账龄口径 | 分档标准（30/60/90/180 还是按合同账期起算）、起算日取单据日还是发货日 |
| 客户分类 | 商超 / 电商 / 外贸 / 授权商各自的标准账期与结算习惯 |
| 不催清单 | 关联方、质保金、模具费尾款、已进入法务流程的——**出现在催收清单里就是事故** |
| 玩具行业特有 | 模具费 / 开模费的核算与摊销口径、退货与折让处理（玩具退货率高）、认证费用归集 |
| 外销相关 | 汇率折算口径、退税周期对账龄的影响 |
| 催收动作 | 话术分级（首次提醒 / 正式函 / 停货预警）、谁抄送、哪些客户禁止直接发 |
| 交付格式 | 报表模板、发送对象与时点 |

> 获取方式有个一举两得的做法：直接要客户过去 3–6 个月**已经做完的那几张表**。人工表里隐含着全部口径，同时它正好就是 4.7 的评测真值集。

### 4.7 最小 eval：本客户从"可选"变成"必须"

通用 POC 里 eval 可以推到 Phase 2；**本客户不行**——财务场景的验收标准必然是"数字对不对"，而且没有"95% 准确"这回事：一个数字错，整张表作废。

它不是评测框架，只有三样东西：

| 组成 | 内容 | 本客户的形态 |
|---|---|---|
| **冻结的用例集** | 真实输入 + 期望输出 | 3–6 个历史月份的用友取数**快照** + 财务当时人工产出的那几张表 |
| **可自动判分的断言** | 有真值就断言，别用模型打分 | 见下表 |
| **可重复的 runner** | 一条命令跑全集，输出通过率与逐条 diff | 结果写回 Run Log |

分两层评，不要混为一谈：

| 层 | 断言什么 | 目标 |
|---|---|---|
| **确定性层**（取数 · 计算 · 口径） | 应收总额、单据条数、客户数与用友期末报表逐项相等；账龄分档逐格比对人工表；不催清单里的客户不得出现在催收清单 | **100%，差一分钱算失败** |
| **判断层**（催收优先级 · 话术 · 异常识别） | 与财务当时的实际动作比对，如 top10 重合度 | 给区间，不给绝对值 |
| **成本层** | 单次任务 token / 费用 | 有基线即可 |

三条必须守住的设计约束：

1. **用例输入从 Run Log 导出，不手写。** 失败轨迹自动入库成用例，正是功能清单「回归评测集 / 生产数据回流 eval」的机制。所以最小 eval **不是新造子系统，是给 Run Log 加一个导出与重放入口**——它天然零丢弃
2. **必须跑在冻结快照上，不能跑在实时库上。** 用友里的历史单据会被修改，跑实时库的用例不可重复，evaluation 就没有意义
3. **有真值就不要用 LLM-as-judge。** 财务场景难得地拥有 ground truth，这是它相对通用 Agent 评测的巨大优势，别浪费

什么时候会用到它：换模型时、客户改口径时（"账龄改成按合同账期"，改完怎么知道没改坏别的）、以及 POC 验收当天客户问"准确率多少"时。

> 工作量约 2–3 人日，不是一个 sprint。它之所以看起来贵，是因为通常被想象成"评测平台"——这里要的只是一个用例目录、一个断言脚本、一条命令。

### 4.8 交付形态：装在客户设备上的富客户端

**是富客户端，装在客户设备上**——这正是演示时刻 1「数据没走」能成立的前提。但"富"的边界要说准，否则会滑回「客户端即平台」的处境：

> **富在执行，不富在状态。**
> 本地沙箱、文件读写、托管运行时、内置浏览器都在客户端，越重越好；
> 权威状态在 daemon 的 Run Log 里，UI 只是薄接入面（B 类约束，真 IPC）。

**部署位置已定：客户提供一台常开机器跑 daemon，财务电脑只是薄接入面**——POC 期用浏览器打开内网地址，零安装（4.10）。

| | 开发期 | POC 交付形态（已定） |
|---|---|---|
| daemon | 本机 | **客户内网常开机器** |
| UI | 本机（浏览器） | 财务的工作电脑，**浏览器打开，不装东西**（4.10） |
| 定时触发 | — | **满血：周一 8:00 真的自己跑完**，与财务电脑开不开机无关 |

切换只是一个地址——daemon / UI 本来就是真 IPC。顺带还有两个好处：用友服务器同在内网，取数路径更短；财务电脑关机不影响任何事。

> 这就是技术路线那句话的现场实证：**「长时进程守护」与「跨设备接管」不是功能，是部署选项。**
> 也是 POC 期论证 Phase 0 投入最有力的证据——客户当天就受益，而不是"为了 18 个月后进企业"。
> 顺带说明：这台常开机器就是「组织内 Runner」的雏形，但 POC 期它跑的是**同一份 daemon 代码**，不是另一套东西。

三个随之而来的细节，都要按"实现可简陋、接口不可错位"处理：

| 事项 | POC 期做法 | 不可让步的部分 |
|---|---|---|
| **常开机器选什么平台** | 客户 Windows / macOS 都能提供——**优先要 macOS**（见下） | 别接受 Linux：那是第三套平台适配，POC 期不值得 |
| **UI ↔ daemon 认证** | 内网 + 共享 token，极简 | 认证必须是接口的一部分，不能"内网就不认证"——将来收紧只换实现 |
| **产物怎么回到财务手上** | 企业微信推送（4.9）+ UI 内下载 | 产物必须是标准格式、可导出，不锁在客户端里 |

**平台选择：让跨平台的负担落在薄的那一侧。**

客户 Windows / macOS 都能给，那就要 **macOS 常开机跑 daemon**：

| | 跑在哪 | 平台 | 理由 |
|---|---|---|---|
| **daemon**（重：沙箱、执行、取数、Run Log） | 客户内网常开机 | **macOS** | 与团队开发机同构，沙箱直接用技术路线首选的 `sandbox-exec`，POC 期少一整套适配 |
| **UI**（薄接入面） | 财务电脑的浏览器 | **与平台无关** | Web 技术栈，由 daemon 直接 serve；桌面外壳推迟到产品期再套（4.10） |

跨平台的成本因此只落在 UI 上，而 4.10 又把这一侧压到接近零——这是 daemon / UI 分离在工程上的又一次红利。若客户 IT 不接受 Mac 进办公网（制造业常见），退回 Windows daemon，届时沙箱按 0.2 白名单简化处理即可，**不要为此推迟开工**。

用友取数不受影响：无论走 API 还是数据库直连，macOS 都连得上内网的用友服务器。

**话术要跟着改准确**：现在的承诺是「数据不出**客户内网**」，不再是「不出本机」。这仍然是强承诺、仍然可当场验证，但说错了会被客户的 IT 当场指出来。演示时刻 1 相应改为在常开机器上断掉除模型 API 外的全部出口。

**原「客户端必须是 Windows」这条排期风险，现已缩小到半条。**

原先的担心是"财务电脑必然是 Windows、团队开发机是 macOS，要多背一套适配"。定了 4.10 的浏览器形态之后：

- **沙箱原语不同这一条不再成立**——沙箱在 daemon 侧，而 daemon 跑 macOS。它只在退回 Windows daemon 时才回来（届时按 0.2 白名单简化：进程隔离 + 工作目录白名单，不上 AppContainer）
- **剩下的半条仍要验，但位置变了**：用友导出的 GBK 编码、路径分隔符发生在 daemon 侧（取数与出表都在常开机上），Windows 这一侧只剩"页面在财务的 Edge 里打得开、产物下得来、能被 Windows 版 Excel 正常打开"

建议 M2 结束前在财务的真实电脑上开一次页面、下载一次产物——十分钟的事，但不要留到 M3 彩排。

### 4.9 外发与审批通道：企业微信

**先把两个用途分开，它们的风险等级完全不同：**

| 用途 | 怎么走 | 说明 |
|---|---|---|
| **内部推送与审批**（周一出表、待批提醒、按业务员派发跟催任务） | **企业微信** | 完美契合，见下 |
| **对外催收**（触达客户） | **业务员手动发，系统不碰** | 已确认。玩具行业业务员与客户是私人关系，AI 代发反而不合适 |

> **由此得到一个对 POC 极有利的结论：整个 POC 期，系统不会对外发出任何一条消息。**
> 唯一的写操作是本地文件，唯一的外发是企业微信内部推送。
> 这可以直接作为承诺讲给客户——放权门槛降到最低，第一周就能全量跑，完全吻合第三节②的放权节奏。

**内部推送这一路的价值被低估了**——它直接兑现 A 类第 5 项「异步审批」，而且是最自然的形态：

> Agent 挂起 → 企业微信推送到手机 → 人在手机上看到影响清单 → 放行 → 任务自动续跑。
> 演示时刻 2 有了最好的载体，还顺带把"审批不必坐在电脑前"演了。

**实现选型，POC 期只有一个正确答案：**

| 方式 | 能力 | POC 期 |
|---|---|---|
| **群机器人 webhook** | 一个 URL 直接 POST 消息到群，零审批、零 corpid/secret | ✅ **选它** |
| 企业应用 + 交互式按钮回调 | 能在企业微信内直接点按钮批准 | ❌ 需要公网回调地址 |

第二种要当心：企业微信的服务器在公网，按钮回调必须打到一个公网入口——**这正是技术路线警告过的那个坑：不要因为需要一个 webhook 入口，就顺势把整个控制面搬上云。**

POC 期的正确形态：**企业微信推送消息（附带一个链接）→ 人点链接回到客户端 UI 上批准。** 异步性完全成立，零公网依赖。手机上直接点按钮批准是 Phase 1 的事，那时才该做那个极薄的 webhook 接收端。

### 4.10 UI 技术形态：Web 栈 + 可选外壳

| 层 | 选型 |
|---|---|
| **界面本体** | **TypeScript + React + Vite**，纯 Web，不含任何桌面 API |
| **桌面外壳** | **Tauri 2**（Electron 为保底）——**POC 期不做** |
| **UI ↔ daemon** | WebSocket（订阅 Run Log 事件流）+ HTTP/JSON-RPC（下命令），不走外壳的原生桥 |
| **POC 交付** | daemon 直接 serve 这份产物，财务电脑浏览器打开，**零安装** |

**① 跨平台成本不在框架，在调用点。**

这是零章那条判据在 UI 上的形态。UI 里只有两类代码会被平台绑死，换框架解决不了，边界画对了自动消失：

| 调用点 | 错位写法（将来换外壳要重写） | 正确写法 |
|---|---|---|
| 读状态 | UI 直接读 SQLite / 读文件，或用外壳的 `invoke` 拿业务数据 | 只有一个 `daemonClient` 模块，全部状态经 RPC；内核本来就是事件溯源，**UI 天然是事件流的一个投影**，不轮询 |
| 用原生能力 | 组件里散落 `@tauri-apps/api` / `ipcRenderer` | 收进一个 `platform` 接口，**方法数不超过 5 个**：选文件、打开外链、系统通知、托盘/自启、退出 |
| 认证 | 「内网就不认证」 | token 从第一天就在协议里（4.8） |

守住这两条，**换外壳 = 重写那一个适配器，两天的事**。所以外壳选型不值得纠结；该纠结的是别让它渗进业务代码——UI 里到处 `invoke`，就是红线 1 的前置形态。

**② POC 期先只出浏览器形态。**

daemon 在内网常开机，财务电脑本来就只是薄接入面，那它可以就是一个浏览器标签页：

- 财务电脑零安装：不签名、不申请装软件审批、不碰 WebView2 老镜像问题
- 4.9 的「企业微信推链接 → 点开批准」天然成立；手机点开就是同一个页面（responsive 即可），Phase 1 的移动审批不用另写 app
- 4.8 那条 Windows 排期风险随之塌缩为"在财务的 Edge 里打开看一眼"

桌面外壳留到产品期再套——托盘、开机自启、拖文件进来、原生通知、单机版（daemon 与 UI 同机）才需要它。**同一份 Vite 产物两种加载方式，零分叉。**

**③ 外壳选 Tauri 而不是 Electron，决定性理由是最后一行。**

| | Tauri 2 | Electron |
|---|---|---|
| 安装包 | 3–10 MB | 80–150 MB（制造业 IT 会问一个查账表的工具凭什么 150M） |
| 是否需要 Rust | 需要，但**只在外壳里，约 200 行**——业务全在 daemon | 不需要 |
| Windows 依赖 | WebView2 Runtime（较新镜像已预装，老镜像需离线包或固定版本） | 无 |
| 渲染一致性 | WKWebView(mac) / WebView2(Win) 有差异 | Chromium 全平台一致 |
| 多 webview（产物区内置浏览器） | 支持，成熟度需届时验证；POC 期 iframe 足够 | `WebContentsView` 成熟 |
| **红线 1** | 主进程没有 Node，**想把 Agent Loop 塞进 UI 都塞不进去** | main 进程有完整 Node，诱惑长期存在 |

不选 Flutter / MAUI / Qt：产物区要渲染 diff、HTML 预览、Markdown、密集表格，最后仍要嵌 webview，等于绕一圈回到 Web，还多背一套人才成本。

**④ 依赖清单（POC 期定这些就够）：**

| 用途 | 选型 | 备注 |
|---|---|---|
| 组件库 | **Ant Design 5** | 财务用户、密集表格、zh-CN 期间选择器最省时间；"允许难看"的前提下不要自研设计系统 |
| 表格 | AntD Table；上万行时换 TanStack Table + 虚拟滚动 | 账龄明细行数可能很大 |
| diff / 代码 | Monaco DiffEditor | 产物 diff、4.4② 回写 dry-run 的凭证清单比对 |
| 状态 | TanStack Query（服务端状态）+ Zustand（UI 状态） | **不要把 Run Log 塞进前端全局 store**——它是 daemon 的，前端只缓存 |
| 传输 | 原生 WebSocket + 极薄手写 JSON-RPC | 不上 tRPC / gRPC-web：daemon 语言未定时会被绑死 |
| Excel 预览 | daemon 输出 JSON，前端渲染表格 | 前端不解析 xlsx |

**⑤ 唯一现在就要定死的东西：契约层。**

monorepo 里一个 `packages/protocol`，只放 Run Log schema 的类型定义与 RPC 定义。daemon 已定 Rust（4.11⑤），因此这层的 TS 类型**从 Rust 侧生成**，不手写两遍。其余（组件库、外壳、状态库、传输细节）全部可换，这正是"允许实现简陋，不允许调用点错位"在 UI 侧的落点。

### 4.11 开源件复用边界：只借实现，不借架构

评估对象：**openai/codex**（Apache-2.0，实测 `main` 分支，2026-08-29）。结论一句话：

> **拿它的沙箱与出口代理，不拿它的内核、Run Log 与协议。**

规模先摆清楚：`codex-rs` 约 100 个 crate、3433 个 `.rs`、**约 153 万行 Rust**，其中 `core` 一个 crate 就 35 万行。fork 等于接管一个比本产品大一个数量级、且上游在高速改动的代码库。

**① 它确实已经做好了功能清单的一大半——这部分不复用是浪费**

| 本文的项 | codex 里的对应件 | 判断 |
|---|---|---|
| A 类 10 网络出口白名单 | **`network-proxy`**：本地 HTTP + SOCKS5 代理，allow/deny 列表与通配、HTTPS MITM 钩子、**OTEL 结构化审计事件**、向子进程注入 `HTTP(S)_PROXY` | **正是本文要求的"本地 forward proxy 层"**，自研至少两周且容易做错 |
| A 类 2 / 地基 D 本地沙箱 | `sandboxing` + macOS `sandbox-exec` + `linux-sandbox`(landlock/seccomp) + **`windows-sandbox-rs`（2.1 万行，含 ACL / audit / conpty）** | 三平台齐活；Windows 那套尤其值钱（4.8 退回 Windows daemon 时直接兑现） |
| A 类 9 MCP 接入 | `codex-mcp` / `rmcp-client` / `mcp-server` | 成熟 |
| A 类 11 流程库 | `skills` + plugin manifest（声明 skills / mcp_servers / hooks / apps） | 承载方式与 0.3 一致：以数据存在，不进代码 |
| 高危命令口径 | `execpolicy` | 可直接作为 Gateway 策略钩子的实现 |
| 0.2 密钥 | `secrets` + `keyring-store` | 命中白名单该行 |
| 4.3 加分项 文件变更触发 | `file-watcher` | 顺手 |

**② 三处硬冲突——决定了它不能当主干**

| # | 冲突 | 实测依据 | 后果 |
|:---:|---|---|---|
| 1 | **模型只剩 Responses API** | `WireApi` 枚举现在**只有一个变体 `Responses`**，`wire_api = "chat"` 已删除并直接报错 | 国内财务客户几乎不可能走 OpenAI；接 Claude / DeepSeek / 通义都要先架 `/v1/responses` 兼容层。**要撑开的正是上游在收窄的接口**，每次合并都要重打 |
| 2 | **`rollout` 是会话转录，不是 Run Log** | `RolloutItem` 的变体为 `SessionMeta / ResponseItem / EventMsg / TurnContext / WorldState / SecurityRiskScore / Compacted / RealtimeItem`；`TokenUsage` **只有 token 数**，唯一的 `estimated_usage_usd_micros` 来自 `backend-client`（向 OpenAI 后端查） | 换任何别的供应商，A 类第 7 项**一个金额都拿不到**；`approval.*`、`cost.charged`、`cite` 字段全不在；且 `Compacted` 会压缩历史，与"审计原件"直接冲突。在它旁边另建一套 = 回放、成本、审计三套数据对不上账 |
| 3 | **扩展点是观察者，不是拦截器** | `ext/extension-api` 的 `tool_lifecycle` 回调返回类型是 `()`——能看不能改；`Blocked` 是宿主自己的决定 | Effect Gateway 这个唯一收敛点若要建在它上面，只能改 `core` 那 35 万行——**那是 fork，不是集成**。另：全仓没有跨工具统一的 dry-run，`apply_patch` 的 diff 是单工具特性，正是红线要避免的"每个工具各写预览模式" |

补充三条同向事实：**没有调度器**（全仓无 cron/scheduler，A 类第 8 项自建）；`app-server-daemon` 是**进程生命周期管理器**（面向 SSH / 远程机），不是"任务活得比 UI 久"的那种 daemon；`core` 到处读时钟与环境变量，B 类「内核确定性 + 构建期静态检查」在 fork 上不可能成立。

**③ 三档方案，取第 ②**

| | 做法 | 判据裁决 |
|---|---|---|
| ① fork 全仓当主干 | 改 `core` 加 Gateway / Run Log / 成本 | ❌ "调用点错位"的最严重形式——调用点全是别人的；7.2 自检第 5 条（丢弃 < 5%）必然过不了 |
| ② **自研 daemon 与内核，crate / 进程级依赖它的若干实现** | 见下 | ✅ 拿的几样**全部落在 0.2 白名单里**：它们是实现，被 Gateway 与执行面接口包着 |
| ③ 完全不用 | | 浪费——沙箱与出口代理是最贵且最容易做错的两块 |

**拿**：`network-proxy`（独立进程，daemon 把沙箱子进程的 `HTTP(S)_PROXY` 指过去）、`sandboxing` / `windows-sandbox-rs` / `linux-sandbox`（作为地基 D「本地沙箱」这一种实现）、`execpolicy`（Gateway 策略钩子的实现）、`apply-patch`（产物 diff）。

**不拿**：`core`（agent loop）、`rollout`（Run Log 必须是本文的最终 schema）、`tui`、`app-server-protocol`（UI 协议应当长成 Run Log 的投影，不是它的会话协议）、`login` / `chatgpt` / `backend-client` / `analytics`（OpenAI 账号与遥测体系）。

> 最后一组尤其要当心：codex 默认带 OTEL、analytics、ChatGPT 登录、cloud-tasks。若走 ① 档必须逐个摘干净，否则**演示时刻 1「断掉除模型 API 外的全部出口」当场翻车**——而这部分清理 100% 是纯丢弃。

**④ 合规与话术**：产品含 Apache-2.0 代码需保留 LICENSE / NOTICE。客户安全评审会问"是不是套了 OpenAI 的壳"——② 档答起来干净（"沙箱与出口代理用了开源组件"），① 档答不干净。

**⑤ daemon 语言：Rust（已定）**

团队有熟悉 Rust 的同事，② 档因此走完整形态：**crate 级依赖**，而不是跨进程调二进制。随之确定三件事：

| | 结论 |
|---|---|
| daemon | Rust，直接 `cargo` 依赖 `network-proxy` / `sandboxing` / `execpolicy` / `apply-patch` |
| 契约层 | `packages/protocol` 的 TS 类型**从 Rust 侧生成**（codex 自身即用 `ts-rs`，可照搬这套做法） |
| 外壳 | 与 4.10 的 Tauri 同语言，将来套外壳时没有第二套工具链 |

> 仍要守住的一条：**依赖是 crate 级，不是 fork 级。** 这几个 crate 一旦需要改上游才能用，就说明借错了层——退回把它当子进程用（`network-proxy` 与沙箱执行器都能以子进程 + JSON-RPC 调用），而不是往上游打补丁。这条是 ① 档与 ② 档的分界线，排期紧张时最容易被越过。

## 五、演示剧本（四个时刻）

POC 现场只需要四个瞬间，其余都是铺垫：

| # | 时刻 | 在本客户身上怎么演 |
|---|---|---|
| 1 | **"数据没走"** | 在常开机器上断掉除模型 API 外的所有出口，从用友取数到生成账龄表全程照跑；打开出口日志——只有模型 API 一条，财务明细一条没出内网（4.8） |
| 2 | **"它先问了我"** | 主载体是 **4.4② 的用友回写 dry-run**：当场给出将写入的凭证清单、科目、金额、影响期间，一条不落、一条不写。辅以推送范围确认——跟催任务包含客户欠款金额，推错人就是事故，推送对象要人点过才发 |
| 3 | **"我下班了它还在干"** | 关掉 UI，周一 8:00 定时跑完；到岗前企业微信里已经躺着账龄表、催收清单和本次花了多少钱 |
| 4 | **"这一步为什么这么干"** | 财务问"这家客户账龄怎么算成 90 天以上"，点开回放到取数那一步：读了哪张表、套了哪条口径、挂回哪张单据 |

> 注意：对外催收既然由业务员手动完成，原本"催收邮件发不发"这个最有张力的确认点就没有了。**时刻 2 的重量必须由回写 dry-run 接住**，否则整场演示会缺一角——这也正是 4.4② 存在的意义。

第 4 个时刻在财务客户身上是**验收关键而非锦上添花**——财务人员的默认假设是"数字是编的"，回放加溯源是唯一能消解这个假设的东西。

四个时刻必须跑在**客户自己的真实任务**上。任何一个需要预置数据才能演，说明越过了红线 5。

## 六、排期

假设 3–4 人工程团队，请按实际调整。全程在主干开发，不开 POC 分支。

| 里程碑 | 周期 | 内容 |
|---|---|---|
| **M0 前置**（客户侧） | 第 1 天 | ① 取只读账号（随时可得，同时确认版本）② **向财务要 3–6 个月的人工成品表**——口径库素材与评测真值一次拿齐（4.6 / 4.7）。②是当前唯一的客户侧依赖 |
| **M1 地基** | 2 周 | daemon 边界 + Run Log schema + Gateway（只记账）+ 本地沙箱执行（**沙箱与出口代理直接依赖开源 crate，不自研**，见 4.11） |
| **M2 可演示** | 2 周 | A 类 1 / 2 / 3 / 4 / 5 / 9 / 11 / 12 / 13 + 用友 MCP Server（导出通道实现）+ 4.5 的交付物 1、2 + **在客户那台常开机器 + 财务 Windows 电脑的组合上完整跑通一遍**（4.8） |
| **M3 可评审** | 2 周 | A 类 6 / 7 / 8 / 10（第 10 项成本已因 4.11 大幅下降，主要工作在策略配置与出口日志展示）+ 4.5 的交付物 3、4 + 最小 eval（4.7）+ 实时接口接上（若账号已到）+ 剧本彩排 |

**压缩预案（客户只给 2–3 周）**：砍掉第 8 项（触发器）与第 6 项的回放 UI（只留 Log 导出），其余 A 类保留；**B 类五项、第 13 项溯源、4.7 的确定性层 eval 一条都不能砍**——前者砍掉省下不足一周而代价是一个季度，后两者砍掉直接砍掉本客户的验收依据。

账号随时可得后，M0 已不构成阻塞（4.3）。唯一要盯的是财务那批历史成品表能不能按时拿到——拿不到，4.6 口径库与 4.7 评测集同时落空。

## 七、出场判据

### 7.1 POC 是否成功（客户侧）

1. 四个演示时刻全部跑在客户真实任务上，无预置数据
2. 客户能独立复现其中至少一次完整任务
3. 数据流向、审计留痕、成本三个问题现场能答且能当场验证
4. **确定性层 eval 全集 100% 通过，且能当场跑一遍给客户看**（4.7）——财务客户的验收就是这个数字，含糊不过去

### 7.2 POC 是否零丢弃（内部自检——POC 结束当天做）

| # | 自检项 | 期望 |
|---|---|---|
| 1 | 代码库里有没有名为 demo / poc / mock 的分支、目录、开关？ | 零 |
| 2 | 删掉全部"演示用"配置后，产品还能不能正常跑？ | 能 |
| 3 | 新接入一个工具，需不需要改治理代码才能获得 dry-run 与记账？ | 不需要 |
| 4 | 客户 A 的全部定制，能不能不改一行代码换成客户 B？ | 能 |
| 5 | POC 期写的代码，预期在 Phase 1 会被删掉多少？ | < 5%，且必须能指名道姓说出是哪几处 |

第 3 条是技术路线第七节判据 1 的 POC 期弱化版。**它做不到，说明 Gateway 被做成了一个转发函数**——那是红线 2 的另一种表现形式。

## 八、已确认与待确认

### 已确认

| # | 问题 | 答案 | 落到哪 |
|---|---|---|---|
| 1 | 客户与场景 | 玩具行业，办公场景，与用友财务软件对接 | 第四节；A 类第 9 / 11 项已具体化，新增第 13 项 |
| 2 | 验收标准 | 财务场景必然是"数字对不对" | **最小 eval 由此从 Phase 2 提前进 POC**，见 4.7 |
| 3 | 用友版本 | 暂不确认，先做容易的 | **已解耦**：语义接口先定，版本差异关在 MCP Server 内部；取账号时版本自然明确（4.2） |
| 4 | 只读账号 | **客户确认可批** | 实时接口从"可能没有"变为"确定会有"，剩余未知只是时长（4.2 / 4.3） |
| 5 | 主线场景 | **B：应收账龄 + 回款跟催** | 交付物已定，见 4.5 |
| 6 | 交付形态 | **富客户端，装在客户设备上** | 见 4.8；新增 Windows 环境这一排期风险 |
| 7 | 外发通道 | **企业微信** | 见 4.9；内部推送与审批走它，**对外催收通道另需确认** |
| 8 | 账号审批时长 | **随时可得** | 实时接口升为第 1 实现，导出通道降为兜底（4.2）；M0 头号风险消失（4.3） |
| 9 | 常开机器 | **客户可提供** | 部署形态定稿为「daemon 在内网常开机 + UI 在财务电脑」，演示时刻 3 满血（4.8） |
| 10 | 对外催收通道 | **业务员手动发，系统不碰** | 交付物 3 改为按业务员分组的跟催任务包；**演示时刻 2 的载体改为回写 dry-run**（4.9 / 第五节） |
| 11 | 常开机器平台 | **Windows 或 macOS 皆可** | **优先要 macOS 跑 daemon**——跨平台成本只落在薄的一侧（4.8） |
| 12 | UI 技术形态 | **Web 栈（TS + React），POC 期浏览器打开、零安装** | 见 4.10；桌面外壳（Tauri 2）推迟到产品期，4.8 的 Windows 排期风险随之缩小 |
| 13 | 开源件复用边界 | **借 codex 的沙箱与出口代理，不借内核 / Run Log / 协议** | 见 4.11；A 类第 10 项与第 2 项的实现成本大幅下降 |
| 14 | daemon 实现语言 | **Rust**（团队有熟悉 Rust 的同事） | 4.11⑤ 走完整形态：crate 级依赖；契约层 TS 类型从 Rust 生成 |

### 待确认

**无阻塞项，可以开工。**

唯一的客户侧关键路径是 M0 那批**历史 3–6 个月的人工成品表**——它同时是口径库素材（4.6）与评测真值（4.7），拿不到这两样一起落空，值得第一天就开口要。

M2 期间会自然浮现、届时再定即可的次要问题：话术分级的具体措辞、账龄表最终版式、跟催任务包推给业务员个人还是业务组、业务员反馈（"已联系 / 承诺 X 日付款"）要不要回流——最后一项是 Phase 2「人机混合队列」的入口，**POC 不做，但值得在现场提一句**，那是客户最容易看见下一步价值的地方。
