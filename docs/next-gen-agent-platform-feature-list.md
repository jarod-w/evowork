# EVOWORK · 功能清单

> 本文档定义 **EVOWORK**（我们要做的下一代智能体平台，即本仓库）的功能范围。
>
> 与 [agent-platform-feature-list.md](agent-platform-feature-list.md)（对标平台盘点）区分：那份是「现在的智能体平台长什么样」，这份是「EVOWORK 应该长什么样」。**怎么做到**见 [next-gen-agent-platform-tech-roadmap.md](next-gen-agent-platform-tech-roadmap.md)。
>
> 注：对标平台（腾讯 EvoWork）与本产品同名，文档中一律以大小写区分——`EVOWORK` 指我们的，`EvoWork` 指对标平台。
>
> 核心命题：**平台的竞争力不在 Agent 有多能干，而在用户敢让它干多少。** 当能力被模型迅速拉平，差异落在放权深度上——能否放心把生产系统的写权限交出去。

## 零、设计原则

所有功能取舍服从以下五条，冲突时按序号优先：

| # | 原则 | 落地判据 |
|---|------|---------|
| 1 | **放权优先** | 每个功能都要回答：这让用户敢多放一点权吗？不能回答的，降优先级 |
| 2 | **默认可审计** | 任何 Agent 动作可回放、可归因、可举证。审计不是开关，是地基 |
| 3 | **声明式优于命令式** | 用户声明期望状态，Agent 持续收敛；而非用户编排步骤 |
| 4 | **不在脚手架上建护城河** | 会被下一版模型吞掉的层（提示工程、模式切换、手写编排、通用技能）保持薄，随时可弃 |
| 5 | **成本是一等公民** | 并发、预算、配额内建于内核，不是事后加的仪表盘 |

**图例**：
- 属性 — 🏛 **沉淀**（长期护城河，随规模增值） / 🔧 **脚手架**（随模型进步变薄，保持轻量可弃）
- 优先级 — **P0** 首发必备 / **P1** 第二阶段 / **P2** 观察期

## 二、意图与交互

| 功能 | 说明 | 属性 | 优先级 |
|------|------|:----:|:------:|
| **决策 Inbox** | 主界面不是输入框而是待决策队列：Agent 提议，人做判断（批准/驳回/改条件）。输入框降级为其中一种入口 | 🏛 | P0 |
| **异步审批** | 高危操作不阻塞执行：Agent 挂起 → 推送通知 → 人在任意设备放行 → 自动续跑。取代同步弹窗 | 🏛 | P0 |
| **声明式目标** | 用户声明期望状态（「这份看板始终反映最新数据」），Agent 持续 reconcile，而非一次性任务 | 🏛 | P1 |
| **产物双向编辑** | 产物是共享画布不是只读交付物：人直接改其中一段，Agent 感知 diff 并在改动基础上继续 | 🏛 | P1 |
| **跨设备接管** | 桌面发起、手机审批、云端续跑，任务状态跟人走 | 🔧 | P1 |
| **澄清式追问** | 需求不明确时主动问一句，而不是猜着做完再返工。问题带默认选项，一键回答 | 🔧 | P0 |
| **嵌入式入口** | 除独立工作台外，内嵌 IDE / 办公套件 / 企业 IM / 浏览器的 inline agent | 🔧 | P2 |
| **执行过程可折叠** | 默认看结论，可展开到每一步工具调用；长任务给进度与预计剩余 | 🔧 | P0 |

## 三、触发与常驻（Ambient）

| 功能 | 说明 | 属性 | 优先级 |
|------|------|:----:|:------:|
| **事件触发** | webhook / 文件变更 / 邮件到达 / IM 消息 / CI 失败 / 日历变更 / 工单创建，均可作为触发源 | 🏛 | P0 |
| **条件触发** | 监控指标偏离阈值时唤醒（如「库存低于 X」「错误率突增」） | 🏛 | P1 |
| **定时触发** | 一次性 / 周期性（日/周/月/年）、生效期、暂停恢复 | 🔧 | P0 |
| **去抖与合并** | 高频事件自动合并为一次执行，防止风暴 | 🔧 | P0 |
| **干运行（dry-run）** | 触发器上线前先空跑：只报告「会做什么」，不实际执行 | 🏛 | P0 |
| **影响预估** | 执行前给出将触碰的文件/系统/外部调用清单与预估成本 | 🏛 | P0 |
| **触发限流与熔断** | 单位时间执行上限、连续失败自动暂停并告警 | 🏛 | P0 |
| **执行历史** | 每次触发的输入、决策链、产物、成本、结果留档 | 🏛 | P0 |

## 四、编排与多智能体

| 功能 | 说明 | 属性 | 优先级 |
|------|------|:----:|:------:|
| **Agent Fleet 并行** | 一个目标拆给多个 Agent 并行推进，统一汇总 | 🔧 | P0 |
| **隔离执行** | 并行 Agent 各自在独立工作副本（worktree / 沙箱快照）中改文件，避免互相踩踏，合并时做冲突消解 | 🏛 | P0 |
| **预算闸门** | 每个任务/子 Agent 有 token、时长、并发数、递归深度上限，超限自动挂起而非静默烧钱 | 🏛 | P0 |
| **检查点与续跑** | 长任务定期落检查点，可暂停、可断点续跑、可回滚到任一检查点重跑（time-travel） | 🏛 | P0 |
| **workflow-as-code** | 稳定流程可固化为可版本化、可评审、可灰度的脚本；但不作为主路径 | 🔧 | P1 |
| **动态组队** | Agent 根据任务自行决定拉谁进来，按结果反馈调整组队策略 | 🔧 | P2 |
| **Agent 间通信** | 子 Agent 之间可传递结构化结果与共享工作区，而非只能经主 Agent 中转 | 🔧 | P1 |
| **人机混合队列** | 流程中某一步指定由人完成，Agent 等待并在完成后继续 | 🏛 | P1 |

## 五、验证与交付质量

| 功能 | 说明 | 属性 | 优先级 |
|------|------|:----:|:------:|
| **验收标准前置** | 任务开始前先协商 acceptance criteria，结束时逐条自检并给出通过/未通过，而非丢一份产物 | 🏛 | P0 |
| **对抗式验证** | 生成与校验分离：多个独立 Agent 从不同视角（正确性/安全/可复现/成本）尝试**反驳**结论，多数通过才交付 | 🔧 | P0 |
| **溯源引用** | 报告中每个数字、每条结论可点回原始文件行号或网页片段 | 🏛 | P0 |
| **置信度标注** | 模型不确定处显式标注并主动提问，禁止自信编造 | 🏛 | P0 |
| **可执行验收** | 验收标准本身写成可运行的检查（测试、脚本、断言），交付时自动跑 | 🏛 | P1 |
| **回归评测集** | 失败轨迹自动入库成 eval 用例，后续版本必须通过 | 🏛 | P1 |
| **交付 SLA** | 对特定任务类型承诺准确率区间与错误处置路径 | 🏛 | P2 |

## 七、技能与知识（自进化）

| **内置通用技能** | 文档、表格、演示、图表等基础能力预装——但明确视为**会被模型吞掉的层**，保持薄，不投入重资源 | 🔧 | P0 |

## 九、治理（护城河 · 重点投入）

| 功能 | 说明 | 属性 | 优先级 |
|------|------|:----:|:------:|
| **Agent 身份** | Agent 是 IAM 中的一等 principal，有独立标识；权限只能是发起人权限的**子集**，不可提权 | 🏛 | P0 |
| **policy-as-code** | 「哪些目录可读、哪些连接器可用、哪类操作须审批、单任务成本上限」写成可版本化、可测试、可灰度的策略文件，而非散落开关 | 🏛 | P0 |
| **不可篡改审计日志** | 每次工具调用、每个网络出口、每份产物变更全量留痕，支持合规导出与取证 | 🏛 | P0 |
| **完整执行回放** | 任一历史任务可逐步回放决策链，用于事故复盘与责任认定 | 🏛 | P0 |
| **成本归因** | token / 时长 / 外部调用费用按人、团队、任务、技能四维归因，支持硬性配额与超限熔断 | 🏛 | P0 |
| **数据边界与 DLP** | 声明哪类数据不得出本机 / 不得出境 / 不得进入模型上下文，违反即拦截 | 🏛 | P0 |
| **审批链与 RBAC** | 不同风险等级走不同审批人；企业 SSO 对接 | 🏛 | P1 |
| **放权分级** | 明确的自主度档位（只读 → 沙箱内写 → 授权目录写 → 生产系统写），逐级解锁并可随时收回 | 🏛 | P0 |

## 十、安全（护城河 · 重点投入）

| 功能 | 说明 | 属性 | 优先级 |
|------|------|:----:|:------:|
| **提示注入防护** | 连接器返回、网页内容、他人文档一律标记为**不可信输入**；污点内容不得触发写文件、发消息、调用连接器、支付等提权动作，需人工放行 | 🏛 | P0 |
| **能力安全模型** | 工具调用携带不可伪造的 capability token，权限随调用链收窄而非放大 | 🏛 | P1 |
| **沙箱隔离** | 进程级隔离 + 系统敏感目录硬拦截 + 逃逸行为检测告警 | 🏛 | P0 |
| **密钥托管** | 凭据由平台代持并注入，Agent 上下文中永不出现明文密钥 | 🏛 | P0 |
| **供应链管控** | 技能与 MCP Server 来源校验、签名、运行时行为异常告警（声明只读却在写文件即拦截） | 🏛 | P0 |
| **高危操作分级** | 删除、对外发送、资金、生产变更等按级别处理；确认异步化但不可省略 | 🏛 | P0 |
| **隐私模式** | 全本地执行 + 本地模型，敏感任务零外发 | 🏛 | P1 |

## 十五、路线图

| 阶段 | 主题 | 交付 |
|------|------|------|
| **Phase 1** | 让它成为同事 | 事件驱动触发 + 决策 Inbox + 异步审批 + 干运行/影响预估 + 完整审计与成本归因 + 放权分级 |
| **Phase 2** | 让它交付得可信 | Agent Fleet + 隔离执行 + 检查点续跑 + 验收前置 + 对抗式验证 + 溯源引用 + 提示注入防护 |
| **Phase 3** | 让它进企业生产 | policy-as-code + SSO/RBAC/审批链 + DLP + 组织资产仓库 + 团队协作 + 回放取证 |
| **Phase 4** | 让它复利 | 轨迹自蒸馏 + 回归评测闭环 + 端侧路由 + A2A 与生态 |

优先级排序依据（来自演进推论）：**① 事件驱动+异步审批**是体验代差 → **② 编排与对抗验证**决定完成质量 → **③ 审计/权限/成本**决定能否进企业 → **④ 注入防护**是唯一会真出安全事故的一项 → **⑤ 自蒸馏**决定长期复利。

## 十六、明确的非目标

写清不做什么，与写清做什么同等重要：

| 不做 | 原因 |
|------|------|
| **技能数量 / 连接器数量的军备竞赛** | 长尾靠 Computer Use 和自蒸馏覆盖，堆数量是可被复制的伪壁垒 |
| **Craft / Plan / Ask 式的模式切换 UI** | 模型自己就该判断该不该动手，让用户选模式是把模型的短板转嫁给用户 |
| **精雕细琢的提示词工程层** | 明确的脚手架，下一版模型即抹平 |
| **自研通用大模型** | 资源应投在治理、安全、组织知识这些不被抹平的层 |
| **没有审计的「全自动」** | 无法举证的自动化在企业里不可用，自主度越高越如此 |
| **把产物锁在平台内的封闭格式** | 产物必须是标准格式、可导出、可脱离平台使用 |
