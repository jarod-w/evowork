## 一、为什么不能照搬对标平台的架构

对标平台的架构可以概括为一句话：**客户端 = 运行时 + 状态，云端 = 模型 API**。Agent Loop 是客户端进程内的一个循环，任务状态在内存里，落盘的只有本地 SQLite 里的自动化任务记录。

把功能清单里的 P0 项摊开看，其中有一整组共享同一个前提：

| P0 功能 | 隐含前提 |
|---|---|
| 事件触发 | 客户端不开也要能被唤醒 |
| 长时进程守护 | 任务活得比进程久 |
| 跨设备接管 | 状态不属于任何一台设备 |
| 异步审批 | 执行可挂起、可从别处恢复 |
| 检查点与续跑 | 状态可序列化、可回退 |
| 不可篡改审计日志 | 有权威的、不可被本地改写的事实记录 |
| 完整执行回放 | 决策链被完整保存而非只保存结果 |
| 成本归因 | 记账点唯一且不可绕过 |

**这八项要求的是同一件事：任务状态必须活得比客户端进程久，且必须有权威副本。** 在这套架构下，这八项每一项都得单独打补丁，而且补丁之间对不上账——回放里的步骤、成本报表里的条目、审计日志里的记录会变成三套互不一致的数据。

结论：功能清单的路线图缺了一个阶段。

> **Phase 0 —— 内核奠基与控制面/执行面分离。**
> 它不交付任何用户可见的新功能，交付的是后面四十项功能的可行性。
> 跳过它，Phase 1 会以「能演示、但进不了企业」收场。

```
└──────────────────────────┬─────────────────────────────────┘
                           │
┌──────────────────────────┴─────────────────────────────────┐
│  控制面  Control Plane（可云端托管，也可私有部署）            │
│                                                            │
│   ┌──────────────┐  ┌──────────────┐  ┌────────────────┐   │
│   │ Agent 内核    │  │ Effect       │  │ 上下文装配器    │   │
│   │ 事件溯源状态机 │  │ Gateway      │  │ 记忆·污点·溯源  │   │
│   └──────────────┘  └──────────────┘  └────────────────┘   │
│   ┌──────────────┐  ┌──────────────┐  ┌────────────────┐   │

│   ══ 权威事实：Run Log（append-only 事件流）══               │
└──────────────────────────┬─────────────────────────────────┘
                           │  lease 领取 effect
┌──────────────────────────┴─────────────────────────────────┐
│  执行面  Execution Plane（无状态 Executor，三种同接口实现）    │
│                                                            │
│   本地沙箱          组织内 Runner        云沙箱               │
│   数据不出本机       客户端关机续跑        Fleet 并行扩容       │
└──────────────────────────┬─────────────────────────────────┘
                           │
┌──────────────────────────┴─────────────────────────────────┐
│  模型面  Model Plane   多供应商可插拔 · 端侧/云端路由          │
└────────────────────────────────────────────────────────────┘
```

与对标平台的关键差异只有一条：**权威状态从客户端进程搬到了控制面的 Run Log 上。**其余变化都是这一条的推论。

注意「控制面在云端」不等于「数据上云」：控制面存的是**事件元数据**（谁、何时、调用了什么工具、策略判定结果、成本），文件内容与执行产物仍留在执行面。隐私边界不变，可举证性从无到有。

## 三、四个地基决策

### 地基 A：Agent 内核改成事件溯源状态机

一次任务 = 一条 append-only 的事件流；内核是纯函数 `(state, event) → state`，所有副作用在内核之外。

```
intent.declared      用户/触发器声明意图
  → context.assembled  上下文装配完成（带 trust 与 citation 元数据）
  → plan.step          模型产出一步决策
  → tool.requested     请求一次副作用
  → policy.evaluated   策略判定结果（允许/拒绝/需审批）
  → approval.pending   挂起等待人
  → approval.granted   人在任意设备放行
  → tool.result        执行结果回流
  → checkpoint         可回退点
  → artifact.emitted   产物产生
  → cost.charged       计费事件
  → run.completed
```

**这一次投入同时兑现清单里 13 项独立功能**——它们不是 13 个功能，是同一个机制的 13 个视图：

| 清单功能 | 在 Run Log 上是什么 |
|---|---|
| 检查点与续跑 | 快照 + 重放到任意 offset |
| 完整执行回放 | Log 本身 |
| 异步审批 | 挂起 = 等一个 `approval.granted` 事件 |
| 跨设备接管 | 状态不在客户端，谁都能接 |
| 人机混合队列 / 人机任务交接 | 同上，等待人的事件 |
| 失败归因 | 定位到具体事件节点，而非「执行失败」 |
| 成本归因 | `cost.charged` 事件按四维聚合 |
| 执行 trace 可视化 | Log 的时间线渲染 |
| 执行历史 | Log 的查询视图 |
| 生产数据回流 eval / 回归评测集 | 失败 Log 直接就是用例 |
| 不可篡改审计日志 | Log + hash chain |

**工程约束（第一天就要定下，后补代价极高）：**

1. **事件 schema 从第一天版本化**，回放器必须容忍历史版本——否则半年后所有旧任务不可回放，审计价值归零
2. **禁止在内核里读时钟、随机数、环境变量**。所有非确定性输入必须作为事件写入，否则回放结果与原始执行不一致，回放就不能作为取证依据
3. **模型响应本身是事件**（含请求指纹与响应），回放不重新调模型
4. 快照只是加速，**语义上必须能从零重放**

### 地基 B：单一 Effect Gateway

模型永不直接碰工具。每一次 tool call 走同一条固定管线，无例外：

```
tool.requested
   ↓
① 身份解析      这个 Agent 代表谁行动
② 能力校验      capability token —— 权限只能收窄，不可放大
③ 污点检查      本次上下文含不可信来源？→ 拦截提权动作
④ 策略求值      policy-as-code
⑤ 预算闸门      token / 时长 / 并发 / 递归深度 / 金额
⑥ 影响预估      将触碰的文件、系统、外部调用
   ↓
   ├─ dry-run 模式：写类 effect 降级为 record-only ──┐
   └─ 正常模式：派发到执行面                          │
   ↓                                               ↓
⑦ 记账 + 审计事件  ←───────────────────────────────┘
```

**治理层与安全层的全部 P0，都落在这一个组件上。**这是护城河能否成立的唯一技术前提：如果这些检查散落在各个工具实现里，它会在接入第 30 个工具时静默漏掉一项，而且你不会发现。

**一个能自检实现是否正确的判据：**

> 干运行不应该是每个工具各自实现的"预览模式"，而应该是 Gateway 的一种**执行策略**。
> 新接入的工具应当天然支持 dry-run 与影响预估，作者不写一行相关代码。
> 做不到这点，说明 Gateway 没做对，而是做成了一个转发函数。

由地基 B 直接兑现：policy-as-code、预算闸门、网络出口白名单、干运行、影响预估、高危操作分级、触发限流与熔断、放权分级、Agent 身份、能力安全模型、密钥托管、供应链运行时管控。

### 地基 C：上下文装配器 + 污点传播

进入模型上下文的每一段内容都携带结构化元数据，而不是拼进 prompt 里：

```
{ source: "connector:feishu/doc/xxx",
  trust:  "untrusted",          // user_direct | org_trusted | untrusted
  scope:  "workspace:team-a",   // 决定谁能看到
  cite:   "c-8f3a" }            // 溯源锚点
```

三条规则：

- **污点会传播**：untrusted 内容参与产生的中间结论继承污点；污点上下文不得触发写文件、发消息、调连接器、支付等提权动作，须人工放行
- **溯源不靠模型自觉**：装配时就分配 `cite` id，输出时**校验**每个数字/结论能挂回一个 id——挂不回的即判定为无依据，直接拦截而非提示
- **记忆权限隔离在装配层做**，不在检索层做：Agent 代表谁行动，就只装配谁有权看的内容

> **反模式警告**：用 system prompt 写「请标注来源」「不要相信网页内容」属于清单第 4 条原则点名的脚手架层——它不仅会被下一版模型抹平，更会被一段精心构造的网页抹平。提示注入防护必须是结构性的，不能是嘱托性的。

由地基 C 直接兑现：提示注入防护、溯源引用、置信度标注、分层记忆、记忆权限隔离、记忆可溯源、数据边界与 DLP、记忆共享给 Agent 群。

### 地基 D：执行面可漂移

Executor 无状态，凭 lease 从控制面领取 effect 执行。同一接口，三种实现：

| 实现 | 隔离原语 | 解决什么 |
|---|---|---|
| **本地沙箱** | worktree + COW 快照；`sandbox-exec`(macOS) / landlock+bubblewrap(Linux) / AppContainer(Win)；**本地 forward proxy 强制出口白名单与全量记账** | 数据不出本机、隐私模式 |
| **组织内 Runner** | 同上，跑在组织服务器 | 长时进程守护、客户端关机续跑 |
| **云沙箱** | 容器 + 网络策略 | Agent Fleet 并行扩容 |

**网络出口必须在 proxy 层管控，不能在 SDK 层拦截。**Agent 会执行任意脚本（`curl`、`pip install`、子进程），SDK 层拦截总有绕过路径，而「出口全量记账」一旦有绕过路径就失去审计意义。

做到这一步，**「长时进程守护」和「跨设备接管」不再是功能，而是部署选项**。

| 阶段 | 技术工作 | 出场判据 |
|---|---|---|
| **Phase 0**<br>内核 | daemon 边界、事件溯源内核、Effect Gateway、上下文装配器、执行面抽象 | 见下节「五条验收判据」全部通过 |

## 六、关键取舍与反模式

### ① 决策 Inbox 的难点不是 UI，是提议质量

一个每天推 50 条待决策的 Inbox 比输入框更糟——它把 Agent 的不确定性全额转嫁给人，恰好犯了功能清单在「非目标」里批评「模式切换 UI」的同一个错误。

必须有一个 `置信度 × 影响半径` 分流器：

```
低风险 × 高置信  → 直接执行，只留审计（Inbox 不出现）
高风险 或 低置信  → 进 Inbox 等决策
不可逆 或 对外    → 强制进 Inbox，且不可批量放行
```

**这个分流策略本身应当是 policy-as-code 的一部分，而不是硬编码。**否则每个组织的风险偏好都要改代码。

### ② 对抗式验证必须真正独立

校验方**只能看到结论和原始材料，不能看到生成方的推理链**。喂了推理链的"验证"是同意机器，多数通过毫无意义。

这个细节决定这项功能是真是假，而它在实现上极易被"顺手复用上下文"破坏。建议在装配器层面硬性约束：验证任务的上下文由独立 profile 装配。

### ③ 分层记忆不要做成向量库优先

「可编辑可遗忘」「冲突消解」「记忆可溯源」「记忆权限隔离」这四项 P0 的本质，是一个**带 ACL 与 provenance 的结构化存储**；语义检索只是它的一个入口。

上来就做 RAG，这四项会无处安放——向量库里删一条 embedding 不等于遗忘，也无法回答「这条记忆来自哪次任务的哪句话」。

### ④ 多模型可插拔（P0）的真实成本在评测，不在 adapter

写 adapter 是几天的工作。真正的成本是：没有回归评测集，换模型就是碰运气，且退化会延迟数周才暴露在用户投诉里。

所以最小 eval 基础设施必须与「多模型可插拔」同期落地，即 Phase 2，不能等 Phase 4。这也是把「回归评测集」提前的唯一理由。

### ⑤ 端侧模型路由（P1）建议后移

它的隐私收益要等 Phase 3 的 DLP 做完才能真正兑现（否则「敏感任务走端侧」中的"敏感"无从判定），而代价是长期维护两套能力边界与两套评测。P1 过早。

### ⑥ 不要建多 Agent 编排框架

功能清单把 Agent Fleet / 动态组队标为 🔧 是准确的判断，值得坚持。**编排与分工能力正在被模型自身吸收**，投入应该在「隔离执行」和「预算闸门」这两项 🏛 上——它们不会被模型吞掉，因为它们约束的是模型本身。

## 七、五条验收判据

Phase 0 是否真的做对了，用这五条自检，不通过就不要进 Phase 1：

| # | 判据 | 验证的地基 |
|---|---|:---:|
| 1 | 新接入一个工具，**不改任何治理代码**，它自动获得 dry-run、影响预估、审计、记账、限流 | B |
| 2 | 杀掉客户端进程，任务能在**另一台设备**上从检查点续跑 | A + D |
| 3 | 任一历史任务可逐步回放，且回放结果与原始执行一致、成本与报表**对得上账** | A |
| 4 | 一段构造的恶意网页内容，**无法导致任何写操作或外发** | C + B |
| 5 | 换一个模型供应商，评测集给出**可比较的分数** | 模型面 |

第 3 条最容易在实现半年后才发现不通过——因为内核里悄悄读了时钟或随机数。建议在内核构建期就用静态检查禁掉。

## 八、技术选型建议

| 关注点 | 建议 | 不建议 | 理由 |
|---|---|---|---|
| 事件存储 | SQLite WAL append-only 表 + 周期快照；服务端 Postgres 同 schema | 起步就上 Kafka | 单任务事件量小，需要的是事务与查询，不是吞吐 |
| 策略引擎 | Cedar 或 OPA/Rego | 自研策略 DSL | 需要的是可测试、可形式化、有生态，自研三样都得重造 |
| 审计防篡改 | hash chain + 周期性外部锚定 | 区块链 | 合规举证只需可验证的不可回溯修改 |
| 进程沙箱 | 平台原生原语（sandbox-exec / landlock / AppContainer） | 起步就全上容器 | 容器在桌面端体验与启动成本都差，且无法覆盖本地文件语义 |
| 网络管控 | 本地 forward proxy 强制出口 | SDK 层拦截 | 见地基 D，SDK 层必有绕过路径 |
| 文件隔离 | git worktree + COW（APFS clonefile / overlayfs） | 全量拷贝工作区 | Fleet 并行下拷贝成本与磁盘占用不可接受 |
| 能力凭证 | macaroon / biscuit 类**可衰减**令牌 | 裸 JWT | 「权限随调用链收窄」要求令牌本身支持衰减 |
| 记忆存储 | 关系型 + provenance/ACL 字段，向量索引作为二级入口 | 向量库优先 | 见取舍③ |
| 事件总线 | 本地内嵌队列起步，组织版再上 NATS / Redis Streams | 起步就 Kafka | 同上 |
| 模型接入 | 统一 adapter + **显式能力声明**（工具调用/视觉/上下文长度） | 各处直接调 SDK | 能力差异不显式声明，降级策略无从实现 |

## 九、起步形态：从零起步的第一版

EVOWORK 是从零起步，所以「第一版长什么样」是一个独立决策，而不是继承来的既定事实。

### 结论：桌面优先——但要害不在这四个字上

桌面优先本身没有争议。需要说清的是一个常被混淆的前提：

> 对标平台的问题**不是**它做了富客户端，而是**客户端同时是权威状态的持有者**。
> 富客户端是对的；「客户端即平台」是错的。
> 这两件事一旦混为一谈，就会得出「所以 EVOWORK 应该云端优先」的错误结论。

桌面优先的四条理由：

| 理由 | 说明 |
|---|---|
| **本地执行是放权的第一级台阶** | 功能清单的核心命题是「用户敢让它干多少」。「数据不出本机」是可**验证**的承诺，云端只能给合同承诺。从最容易被相信的一级起步 |
| **价值密度最高的东西在本地** | 文件、代码仓库、本地服务、已登录的浏览器会话、IDE。云端 Agent 够不到，也最难被复制 |
| **冷启动成本低** | 个人用户装了就能用，不需要企业采购流程。SSO / RBAC / 合规是一年后的事 |
| **早期 Agent 不可靠，需要人在旁边** | 桌面提供最高带宽的介入通道。无人值守是能力成熟后的结果，不是起点 |

### 唯一真正关键的约束

> **从第一天起，Agent 内核跑在独立的 daemon 进程里，不跑在 UI 进程里。**

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  桌面 UI     │   │  IDE 插件    │   │  CLI / 手机  │   ← 都是薄接入面
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       └─────────────────┼─────────────────┘
                    IPC / RPC              ← 这条边界是全部关键
                         │
              ┌──────────┴──────────┐
              │   evoworkd (daemon) │   ← 内核 + Gateway + Run Log
              │   UI 关了它还在跑     │      单机跑本地，组织版跑服务器
              └──────────┬──────────┘
                         │
              ┌──────────┴──────────┐
              │    本地沙箱执行面     │
              └─────────────────────┘
```

这个决策成本极低——多一个进程加一层 IPC——但它一次性买下四样东西：

1. **长时进程守护**：UI 关闭任务继续。清单里的 P1，在这个架构下是免费的
2. **搬到服务端零重写**：同一份 daemon 代码，单机部署在本地、组织版部署到服务器，接口不变
3. **多接入面天然成立**：IDE 插件、CLI、移动端都连同一个 daemon，而不是各写一份 Agent Loop
4. **事件溯源天然成立**：daemon 是唯一写 Run Log 的进程，不存在多写者一致性问题

反过来，把 Agent Loop 写进桌面壳的主进程——最省事、也是多数团队的默认选择——正是对标平台的处境。**这个决策在第 6 个月会变成一次数人月的重写，而且是那种「重写期间出不了新功能」的重写。**

单独强调它，是因为它在整个方案里**成本最低、代价最不对称**：现在做多花一周，将来补要花一个季度。

### 第一版的范围

一句话：**一个能在本地跑、UI 关了还继续跑、每一步都记账可回放的单 Agent 桌面工具。**

从 day 1 就必须正确、后补代价极高的：

| 项 | 第一版做到什么程度 |
|---|---|
| Run Log schema | **必须是最终 schema**，含版本号。可以只存本地 SQLite、可以还没有回放 UI，但字段不能缺 |
| Effect Gateway | 必须存在，但**只做记账与审计**，不加任何拦截，零行为影响 |
| daemon / UI 边界 | 必须是真 IPC，不能是函数调用 |
| 上下文元数据 | 每段上下文带 `source / trust / cite`，哪怕暂时没有消费方 |
| 内核确定性 | 禁读时钟、随机数、环境变量，构建期静态检查 |

可以先砍掉的：Agent Fleet、技能市场、团队协作、组织层记忆、策略引擎（先硬编码规则、留好接口）、对抗式验证、轨迹自蒸馏。

> **第一版的功能面看起来会很像对标平台——差别不在功能清单，而在状态住在哪里。而这个差别决定第 18 个月能不能进企业。**
> 这句话需要对团队讲清楚，否则 Phase 0 的投入会被当成没有产出。

### 云端按什么顺序进来

不是「要不要云」，是「哪一部分先上」：

| 顺序 | 上云的部分 | 时点 | 说明 |
|:---:|---|---|---|
| 1 | 模型 API | Day 1 | 必然 |
| 2 | **webhook 接收端** | Phase 1 | 第一个真正需要服务端的东西——本地机器没有公网入口。可做得极薄：只把事件转发给本地 daemon |
| 3 | Run Log 镜像 / 归档 | Phase 3 | 合规举证需要不可被本地改写的副本 |
| 4 | 云沙箱 | Phase 2+ | Fleet 扩容，可选 |

第 2 项要当心：**不要因为需要一个 webhook 入口，就顺势把整个控制面搬上云。**那是两件事，混起来会让 Phase 1 变成 Phase 3。

### 两个必然会踩的坑

**① 「本地版先跑通，云版以后重写」。** 两版必然分叉，然后云版永远在追赶本地版的功能。正确做法是一套代码、两种部署形态——这正是 daemon 边界要在 day 1 立好的原因。

**② 「个人用户不需要审计和记账，先不做」。** 这两样在 10 个用户、5 个工具时加是几天；在 10 万用户、200 个工具时加是几个月，且要逐个工具改。更要紧的是：**早期的 Run Log 就是 Phase 4 自蒸馏的原料——不存就永远没有，而且补不回来。**

### 什么情况下这个结论会反过来

如果目标客户从第一天就是企业、核心场景是无人值守的系统间自动化、不需要碰用户本地文件——那么云端优先更直接，桌面客户端是负担。

但那是另一个产品。它的对手是 n8n / Zapier 加个 LLM，护城河更薄，因为放弃了本地这层长尾。功能清单把「本地沙箱执行 / 原始数据不出本机」列为 P0，说明选的不是这条路。

## 十、备选路径：若在既有客户端实现上演进

如果 EVOWORK 出于交付压力，需要在一份已有的「客户端即运行时」实现上演进而非重新起步（例如复用某个内部原型），那么以下三步是**唯一可接受的顺序**。三步都是内部重构，**对用户零可见变化**，可与业务开发并行：

**第一步 · 抽内核。** 保留现有客户端 UI 与全部工具实现，把进程内 Agent Loop 抽出为独立 kernel，明确划出「纯决策」与「副作用」边界。此时 kernel 仍跑在客户端进程内，行为不变。

**第二步 · 扩存储。** 本地 SQLite 从「存自动化任务」扩展为「存 Run Log」。**先只写不读**，用真实流量验证事件 schema 的完备性——这一步风险极低，写错了随时改。等 Log 能完整重建出与实际一致的任务状态，再切换读路径。

**第三步 · 收口副作用。** 所有工具调用统一走 Gateway。**第一版只做记账与审计**，不加任何拦截逻辑，确保零行为变化；之后再增量接入 policy、污点检查、capability 校验。

三步走完，**之后每一项治理功能都是「加一条 policy」，而不是「改一遍所有工具」。**

这条路径比从零起步慢，但它避免了「新旧两套并行维护」——那是比重构本身更贵的代价。

## 附二、命名风险

EVOWORK 与对标平台（腾讯 EvoWork）同名，这在三个地方会产生实际成本：

| 场景 | 问题 |
|---|---|
| 对外传播与搜索 | 用户搜不到我们，或搜到的是对方 |
| 商标与合规 | 同类目同名存在争议风险，进企业采购时会被法务问到 |
| 内部沟通 | 文档、issue、会议里说「EvoWork」需要每次消歧 |

技术上无影响，产品上建议尽早决断——改名的成本随代码、域名、包名、品牌资产的积累单调上升，**现在改是改几行文档，一年后改是一次品牌迁移**。

本文档在名称确定前，一律以大小写区分：`EVOWORK` = 我们的，`EvoWork` = 对标平台。
