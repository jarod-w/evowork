## 这一层的难点不是 cron，是「电脑会关机」

云端调度器不会"错过"，机器一直开着。Q1=A 下它跑在用户的笔记本上，合盖一晚上就错过 8 次。
本包一半的代码在回答"那第二天早上用户应该看到什么"。

## 四条不能松的

1. **补偿要落两条记录**（07 §8-1）。一条 `MISSED / MACHINE_OFFLINE` 指向原定时刻，
   一条补跑标注「补跑（原定 …）」。**只留补跑那一条，用户永远不知道自己漏了。**
   这决定的是写库顺序，不只是 UI 文案 —— 所以 `planMisfire` 返回的是**有序动作列表**。
2. **环境原因失败不计入连败**（07 §8-2）。关机中断、路径失效这类失败在笔记本上每周几次，
   计数的话用户的自动化**会在三天内全部被自动暂停**。但它也**不清零** ——
   清零会让"每次失败之间夹一次关机"变成永不暂停。
3. **迁移要重置 misfire 基准**（Q15）。不重置的话用户刚点完「迁移到本机」，
   新机器立刻按补偿窗口扫出一堆历史触发并补跑。
4. **时区显式存储**（07 §3.2）。不依赖运行时系统时区 —— 跨时区出差不该改变触发时刻。

## DST 的两个边界（`cron.ts` 里最值得读的部分）

一个「每天 02:30」的任务，在实行夏令时的时区里：

| 情况                       | 现象                 | 我们的选择                                                        |
| -------------------------- | -------------------- | ----------------------------------------------------------------- |
| 春季跳过（02:00 → 03:00）  | 那天**没有** 02:30   | 在跳变后的第一个瞬间触发（**03:00**）——宁可早半小时，不可少跑一天 |
| 秋季重复（01:00 出现两次） | 那天有**两个** 01:30 | **只触发一次**                                                    |

第一版实现是"UTC 游标每分钟 +1，读本地字段看匹不匹配"，**两个边界都错了**，
是被测试抓出来的：春季整天被跳过，秋季跑了两次。现在按**本地日历日**迭代，
每个「日+时+分」只产生一个候选时刻。

DST 一年只发生两次 —— 错了要等半年才有人报，所以这两条各有一条测试钉着。

## 目录

```
src/
  cron.ts       cron 解析 + **带命名时区**的下次触发 + 未来 N 次预览
  misfire.ts    补偿计划（三种策略）+ 历史文案
  failure.ts    失败分类 + 连败计数 + 自动暂停
  device.ts     设备绑定 + 迁移（乐观锁 + 基准重置 + 路径校验）
  nl.ts         自然语言触发解析（**不调模型**）+ cron 回显
  scheduler.ts  调度循环：扫描 → 触发 → 回写
```

## 为什么 `nl.ts` 不调模型

07 §3.3 的原话：解析在本机完成（规则 + 词表），失败则回落到常用档并提示。
把"设定一个每天跑的任务"的可靠性押在一次模型调用上不合适。
这也意味着**认不出来是正常结果**，所以返回 `undefined` 而不是抛错。

## 还没做的

- **与内核的接线**：`startRun` 现在是注入的端口，真实实现要经 `kernel-adapter`
  起 thread 并带上 `ThreadGoal.budget`（Q11）。
- **wake_system**（07 §4.4）：请求系统定时唤醒。三个平台机制不同，且**不承诺一定能唤醒**。
- **U3 仍未证伪**：真机关机一夜再唤醒的体验。单测能证明"给定这样的时间线，
  落库顺序与文案是对的"，证明不了 OS 的休眠行为。
